script 标签中， async 和 defer 两个属性有什么用途和区别？ ​

参考答案：

在 HTML 中会遇到以下三类 script：

<script src='xxx'></script><script src='xxx' async></script><script src='xxx' defer></script>

script标签用于加载脚本与执行脚本，直接使用script脚本时，html会按照顺序来加载并执行脚本，在脚本加载&执行的过程中，会阻塞后续的DOM渲染。

比如现在大家习惯于在页面中引用各种第三方脚本，但如果第三方服务商出现了一些小问题，比如延迟之类的，就会使得页面白屏。

针对上述情况，script标签提供了两种方式来解决问题，就是加入属性async以及defer，这两个属性使得script标签加载都不会阻塞DOM的渲染。

defer：此布尔属性被设置为向浏览器指示脚本在文档被解析后执行。 async：设置此布尔属性，以指示浏览器如果可能的话，应异步执行脚本。

defer 如果script标签设置了defer属性，则浏览器会异步下载该文件并且不会影响后续DOM的渲染。

如果有多个设置了defer属性的script标签存在，则会按照顺序执行所有的script，defer脚本会在文档渲染完毕后，DOMContentLoaded事件调用前执行。

async async属性会使得script脚本异步的加载并在允许的情况下执行，而async的执行并不会按照script标签在页面中的顺序来执行，而是谁先加载完谁先执行。

CSSOM树和DOM树是同时解析的吗？ ​

参考答案：

浏览器会下下载HTML解析页面生成DOM树，遇到CSS标签就开始解析CSS，这个过程不会阻塞，但是如果遇到了JS脚本，此时假如CSSOM还没有构建完，需要等待CSSOM构建完，再去执行JS脚本，然后再执行DOM解析，此时会阻塞。

前端跨页面通信，你知道哪些方法？ ​

参考答案：

在前端中，有几种方法可用于实现跨页面通信：

  1. LocalStorage 或 SessionStorage：这两个 Web 存储 API 可以在不同页面之间共享数据。一个页面可以将数据存储在本地存储中，另一个页面则可以读取该数据并进行相应处理。通过监听 storage 事件，可以实现数据的实时更新。

  2. Cookies：使用 Cookies 也可以在不同页面之间传递数据。通过设置和读取 Cookie 值，可以在同一域名下的不同页面之间交换信息。

  3. PostMessage：window.postMessage() 方法允许从一个窗口向另一个窗口发送消息，并在目标窗口上触发 message 事件。通过指定目标窗口的 origin，可以确保只有特定窗口能够接收和处理消息。

  4. Broadcast Channel：Broadcast Channel API 允许在同一浏览器下的不同上下文（例如，在不同标签页或 iframe 中）之间进行双向通信。它提供了一个类似于发布-订阅模式的机制，通过创建一个广播频道，并在不同上下文中加入该频道，可以实现消息的广播和接收。

  5. SharedWorker：SharedWorker 是一个可由多个窗口或标签页共享的 Web Worker，它可以在不同页面之间进行跨页面通信。通过 SharedWorker，多个页面可以通过 postMessage 进行双向通信，并共享数据和执行操作。

  6. IndexedDB：IndexedDB 是浏览器提供的一个客户端数据库，可以在不同页面之间存储和共享数据。通过在一个页面中写入数据，另一个页面可以读取该数据。

  7. WebSockets：WebSockets 提供了全双工的、双向通信通道，可以在客户端和服务器之间进行实时通信。通过建立 WebSocket 连接，可以在不同页面之间通过服务器传递数据并实现实时更新。

grid网格布局是什么？ ​

Grid 是 CSS 最强大的二维布局系统，可同时控制行与列的尺寸、位置和对齐，适合复杂整体页面布局；区别于仅能控制单一方向的 Flex 一维布局。

  • grid-template-columns / grid-template-rows

    • 作用：定义列数 / 行数及每列 / 每行的尺寸
    • 取值：
      • fr：按比例分配剩余空间（Grid 独有，最常用）
      • repeat(n, value)：重复生成 n 个相同尺寸
      • minmax(min, max)：尺寸在指定范围内
      • repeat(auto-fit, minmax(200px, 1fr))：一行代码实现响应式列
      • repeat(auto-fill, minmax(200px, 1fr))：自动填充尽可能多的列

  • grid-template-areas

    • 作用：通过命名区域定义布局，语义化极强

    • 示例：

      css
      grid-template-areas:
    "header header header"
    "sidebar main main"
    "footer footer footer";

  • auto-fill vs auto-fit

    • 相同点：都能自动填充尽可能多的列
    • 不同点：
      • auto-fill：保留空单元格，容器宽度足够时会出现空白
      • auto-fit：收缩空单元格，项目会自动拉伸占满整个容器

Flexbox 完整属性速查表（容器+项目） ​

Flexbox 属性分为容器属性（作用于父元素）和项目属性（作用于子元素）两大类，是实现一维弹性布局的核心。

一、容器属性（控制整体布局）

  1. display：定义弹性容器

    • 作用：将元素转换为弹性容器，开启Flex布局
    • 取值：
      • flex：块级弹性容器，独占一行
      • inline-flex：行内弹性容器，宽度由内容决定

  2. flex-direction：主轴方向

    • 作用：定义主轴的方向，决定项目的排列方向
    • 取值：
      • row（默认）：主轴水平向右，项目从左到右排列
      • row-reverse：主轴水平向左，项目从右到左排列
      • column：主轴垂直向下，项目从上到下排列
      • column-reverse：主轴垂直向上，项目从下到上排列

  3. flex-wrap：换行规则

    • 作用：定义项目在主轴上排不下时的换行方式
    • 取值：
      • nowrap（默认）：不换行，所有项目挤在一行
      • wrap：换行，第一行在上方
      • wrap-reverse：换行，第一行在下方

  4. flex-flow：复合属性

    • 作用：flex-direction和flex-wrap的简写
    • 语法：flex-flow: <direction> <wrap>
    • 示例：flex-flow: row wrap;（水平排列，自动换行）

  5. justify-content：主轴对齐方式

    • 作用：定义项目在主轴上的对齐和分布方式
    • 取值：
      • flex-start（默认）：左对齐（主轴起点）
      • flex-end：右对齐（主轴终点）
      • center：居中对齐
      • space-between：两端对齐，项目之间间距相等
      • space-around：项目两侧间距相等，项目间间距是两端间距的2倍
      • space-evenly：项目之间及两端间距完全相等

  6. align-items：交叉轴对齐方式（单行）

    • 作用：定义项目在交叉轴上的对齐方式（适用于单行）
    • 取值：
      • stretch（默认）：拉伸，项目占满整个交叉轴高度
      • flex-start：顶部对齐（交叉轴起点）
      • flex-end：底部对齐（交叉轴终点）
      • center：垂直居中
      • baseline：项目第一行文字的基线对齐

  7. align-content：交叉轴对齐方式（多行）

    • 作用：定义多行项目在交叉轴上的对齐和分布方式（仅在多行时生效）
    • 取值：
      • stretch（默认）：拉伸，每行占满剩余空间
      • flex-start：顶部对齐
      • flex-end：底部对齐
      • center：居中对齐
      • space-between：两端对齐，行之间间距相等
      • space-around：每行两侧间距相等，行间间距是两端间距的2倍
      • space-evenly：行之间及两端间距完全相等

二、项目属性（控制单个项目）

  1. order：排列顺序

    • 作用：定义项目的排列顺序
    • 取值：整数（默认0）
    • 规则：值越小，排列越靠前；支持负数；同值按文档流顺序排列

  2. flex-grow：放大比例

    • 作用：定义项目在有剩余空间时的放大比例
    • 取值：非负整数（默认0）
    • 规则：
      • 0：不放大
      • 所有项目flex-grow都为1：平分剩余空间
      • 一个项目为2，其他为1：该项目占2份，其他各占1份

  3. flex-shrink：缩小比例

    • 作用：定义项目在空间不足时的缩小比例
    • 取值：非负整数（默认1）
    • 规则：
      • 0：不缩小
      • 值越大，缩小得越多

  4. flex-basis：初始尺寸

    • 作用：定义项目在分配剩余空间前的主轴初始尺寸
    • 取值：
      • auto（默认）：由项目内容或width/height决定
      • 长度值（如200px）：固定初始尺寸
      • 百分比（如50%）：相对于容器的百分比

  5. flex：复合属性

    • 作用：flex-grow、flex-shrink、flex-basis的简写
    • 语法：flex: <grow> <shrink> <basis>
    • 常用简写：
      • flex: 0 1 auto（默认）：不放大，可缩小，尺寸由内容决定
      • flex: 1：flex: 1 1 0%，可放大可缩小，平分剩余空间
      • flex: auto：flex: 1 1 auto，可放大可缩小，尺寸由内容决定
      • flex: none：flex: 0 0 auto，不可放大不可缩小，尺寸固定

  6. align-self：单个项目交叉轴对齐

    • 作用：覆盖容器的align-items属性，定义单个项目在交叉轴上的对齐方式
    • 取值：
      • auto（默认）：继承容器的align-items值
      • stretch/flex-start/flex-end/center/baseline：与align-items取值相同

怎么理解回流跟重绘？什么场景下会触发？ ​

在HTML中，每个元素都可以理解成一个盒子，在浏览器解析过程中，会涉及到回流与重绘：

  • 回流：布局引擎会根据各种样式计算每个盒子在页面上的大小与位置

  • 重绘：当计算好盒模型的位置、大小及其他属性后，浏览器根据每个盒子特性进行绘制

回流触发时机 回流这一阶段主要是计算节点的位置和几何信息，那么当页面布局和几何信息发生变化的时候，就需要回流，如下面情况：

  • 添加或删除可见的DOM元素

  • 元素的位置发生变化

  • 元素的尺寸发生变化（包括外边距、内边框、边框大小、高度和宽度等）

  • 内容发生变化，比如文本变化或图片被另一个不同尺寸的图片所替代

  • 页面一开始渲染的时候（这避免不了）

  • 浏览器的窗口尺寸变化（因为回流是根据视口的大小来计算元素的位置和大小的）

重绘触发时机 触发回流一定会触发重绘

可以把页面理解为一个黑板，黑板上有一朵画好的小花。现在我们要把这朵从左边移到了右边，那我们要先确定好右边的具体位置，画好形状（回流），再画上它原有的颜色（重绘）

除此之外还有一些其他引起重绘行为：

  • 颜色的修改

  • 文本方向的修改

  • 阴影的修改

BFC的理解 ​

BFC 是 Web 页面中独立隔离的布局渲染区域，内部元素的布局不会影响外部，外部也不会干扰内部，是 CSS 解决浮动、边距折叠等经典布局问题的核心机制。

触发BFC

  • 浮动元素：float: left/right（值不为none）
  • 绝对定位元素：position: absolute/fixed
  • 溢出控制：overflow: auto/scroll/hidden（值不为visible）
  • 特殊 display 值：
    • inline-block、table-cell
    • flex/inline-flex、grid/inline-grid
    • display: flow-root（现代浏览器推荐，无任何副作用）

解决浮动

  • 使用clearfix伪元素清除浮动，无副作用且兼容性好
  • 给父元素设置高度添加overflow: hidden，适合大多数简单场景
  • 使用display: flow-root，专为创建 BFC 设计，无任何副作用

em/px/rem/vh/vw 这些单位有什么区别？ ​

px：绝对长度单位，对应显示器上的一个物理像素点。 em：相对长度单位，相对于当前元素自身的字体大小；若当前元素未设置字体大小，则继承父元素的字体大小。 rem：相对长度单位，仅相对于 HTML 根元素的字体大小，与任何父元素无关。 vh：相对长度单位，1vh 等于浏览器可视区域高度的 1%。 vw：相对长度单位，1vw 等于浏览器可视区域宽度的 1%。

什么是硬件加速 ​

  • CPU（中央处理器）：计算机的核心控制与运算单元，拥有少量功能强大的复杂核心，擅长处理复杂逻辑判断、串行任务和不规则计算。

  • GPU（图形处理器）：显卡的核心运算单元，采用众核架构，拥有大量结构简单的计算核心，擅长对海量数据执行相同的并行操作，天生适配图形渲染这类重复性高的计算任务。

  • 为什么要硬件加速

    • 浏览器默认渲染流程中，回流（重新计算元素位置大小）和重绘（重新绘制元素内容）是主要性能瓶颈，会触发整个页面的重新渲染
    • 开启硬件加速的元素会被浏览器提升为独立的复合图层，拥有单独的绘图资源
    • 复合图层的位图会作为纹理上传到 GPU，其变化只会触发本层的合成操作，不会引发其他图层的回流和重绘，大幅降低渲染开销

  • 触发方式

    • 强制触发：transform: translate3d(0, 0, 0)（最常用）
    • 动画优化：opacity过渡 / 动画、will-change: transform（提前告知浏览器准备优化）
    • 原生支持：<video>、<canvas>、<iframe>、<webgl>等元素

怎么实现样式隔离？ ​

参考答案：

要实现样式的隔离，你可以考虑以下几种常见的方法：

  1. 作用域样式（Scoped Styles）：

    • 在 Vue 单文件组件中，可以使用 scoped 特性将样式限定于当前组件的作用域。

    • 使用<style scoped>标签包裹的样式只对当前组件起作用，不会影响其他组件或全局样式。

    • Vue 会通过给每个选择器添加一个唯一的属性选择器来实现作用域样式，确保样式仅适用于当前组件。

  2. CSS Modules：

    • Vue 支持使用 CSS Modules 来实现样式的模块化和隔离。

    • 在 Vue 单文件组件中，可以借助 module 特性启用 CSS Modules 功能，在样式文件中使用类似 :local(.className) 的语法来定义局部样式。

    • CSS Modules 会自动生成唯一的类名，并在编译时将类名与元素关联起来，从而实现样式的隔离和局部作用域。

  3. 命名约定：

    • 可以通过使用特定的命名约定来实现样式的隔离。

    • 为了避免样式冲突，可以采用特定的命名规则或前缀，例如 BEM（Block Element Modifier）命名规范或基于组件名称的前缀。

    • 通过在样式类名中添加前缀或特定的命名约定，可以减少样式冲突的可能性。

  4. CSS-in-JS 方案：

    • Vue 也可以结合 CSS-in-JS 库（如 styled-components、emotion 等）来实现样式的隔离。

    • 使用这种方式，可以直接在组件代码中编写样式，并通过 JavaScript 对象或模板字符串的形式动态生成样式。

    • CSS-in-JS 方案将样式与组件紧密关联，实现了更高程度的样式隔离和可重用性。

    1. javascript语言是单线程，就是说同一时间只能做一件事
    2. 为了不阻塞页面，把任务分给同步任务、异步任务
    3. 同步代码直接在主线程执行栈立即执行
    4. 异步任务（定时器、Ajax、dom事件、promise）先进入任务队列排队
    5. 执行栈主线程的任务清空之后，事件循环不断从任务队列取出任务，放到执行栈执行，循环往复，这就是事件循环

  • 异步任务分两种：微任务、宏任务

    • 微任务 优先级更高：Promise.then/catch、async/await后面的代码、queueMicrotask
    • 宏任务：setTimeout、setInterval、Ajax、dom事件、script整体I/O操作

    执行顺序口决：

    先执行同步->再清空所有微任务->再执行一个宏任务->再清空微任务...一直循环 为什么要有事件循环？ 因为js是单线程，如果所有代码都同步阻塞，定时器、网络请求、点击事件都会卡死页面；事件循环让异步不阻塞主线程，保证页面流畅、交互不卡顿

this ​

  • 说说你对js中this的理解

    • this的核心就是：不是函数定义时决定的，而是运行时「调用方式」决定的
    • 普通函数的this是运行时动态绑定的，谁调用它，this就指向谁
    • 没有明确调用主体，就默认指向全局。分四种绑定规则：默认绑定、隐式绑定、显式绑定、new绑定。
    • 箭头函数比较特殊，没有自己的this，会继承外层作用域的this，也没法用call、bind改变

  • this的四种绑定规则是什么

    • 默认绑定普通函数直接裸调用，没有任何对象挂靠，this默认指向全局window
    • 隐式绑定通过对象.方法()这种形式调用，this就指向前面这个对象
    • 显式绑定用call、apply、bind手动强行指定this指向，自己说了算，不依赖调用方式
    • new绑定用new调用构造函数时，会创建一个空对象，并且让this指向这个新实例

  • 普通函数和箭头函数this有啥区别

    • 普通函数没有自己的this，由调用方式决定，可以被call、bind修改指向
    • 箭头函数没有自己的this，沿用外层作用域的this，属于词法绑定
    • 箭头函数不能当构造函数，也没法用call、apply、bind改变this

  • 定时器，回调里为什么会丢失this？怎么解决

    • 因为定时器和异步回调里的函数，最后都是裸调用，走默认绑定，this指向全局，就丢失了原来的实例/对象。
    • 工作里常用三种解决方法：外层保存that=this、用箭头函数继承外层this、用bind提前绑定this

bind、call、apply 有什么区别？如何实现一个bind? ​

  • apply

    apply接受两个参数，第一个参数是this的指向，第二个参数是函数接受的参数，以数组的形式传入

    改变this指向后原函数会立即执行，且此方法只是临时改变this指向一次

  • call

    call方法的第一个参数也是this的指向，后面传入的是一个参数列表

    跟apply一样，改变this指向后原函数会立即执行，且此方法只是临时改变this指向一次

  • bind bind方法和call很相似，第一参数也是this的指向，后面传入的也是一个参数列表(但是这个参数列表可以分多次传入)

    改变this指向后不会立即执行，而是返回一个永久改变this指向的函数

  • 手写bind

    Function.prototype.myBind = function (context) {
    // 判断调用对象是否为函数
    if (typeof this !== 'function') {
        throw new TypeError('Error')
    }

    // 获取参数
    const args = [...arguments].slice(1),
        fn = this

    return function Fn() {
        // 根据调用方式，传入不同绑定值
        return fn.apply(this instanceof Fn ? this : context, args.concat(...arguments))
    }
}

Promise ​

  1. 说一下Promise是什么，解决了什么问题 Promise 是ES6提出的异步编程解决方案，用来统一处理异步回调。主要解决三个痛点：
    1. 解决回调地狱，多层嵌套回调代码可读性极差、难以维护
    2. 统一异步错误捕获机制，不用每层回调单独处理异常
    3. 提供统一链式调用，让异步流程线性书写，可读性更强
  2. Promise三种状态及特点及其实现

  • 三种状态：

    1. Promise 进行中：初始状态
    2. fulfilled 成功
    3. rejected 失败

  • 核心特点：

    • 状态一旦改变就永久凝固，无法再次变更
    • 只能从pending -> 成功 / pending -> 失败
    • 状态不可逆

  • resolve和reject作用

    • resolve()：将状态改为成功，把结果传给后面.then
    • reject()：将状态改为失败，异常传给.catch或then第二个参数

穿透问题/值穿透 如果.then()不传回调函数，会发生值穿透，结果一直向后传递，直到遇到有回调的then或者catch。日常封装公共异步工具经常会利用这个特性。

js
class  MyPromise {
    constructor(executor) {
        this.state = 'pending'; // 初始状态为pending
        this.value = undefined; // 初始值为undefined
        this.onFulfilledCallbacks = []; // 存储成功回调函数
        this.onRejectedCallbacks = []; // 存储失败回调函数
        try {
            // 执行传入的 exector函数，并传入resolve和reject方法
            executor(this.resolve.bind(this), this.reject.bind(this));
        } catch (error) {
            // 如果exector抛出错误，调用reject方法
            this.reject(error)
        }
    }
    // resolve方法，用于将Promise状态改为fulfilled
    resolve(value) {
        if (this.state === 'pending') {
            this.state = 'fulfilled';
            this.value = value;
            // 执行所有成功回调函数
            this.onFulfilledCallbacks.forEach(callback => callback(value));
        }
    }
    // reject方法，用于将Promise状态改为rejected
    reject(reason) {
        if (this.state === 'pending') {
            this.state = 'rejected';
            this.value = reason;
            // 执行所有失败回调函数
            this.onRejectedCallbacks.forEach(callback => callback(reason));
        }
    }
    // then 方法，用于注册成功和失败的回调函数
    then(onFulfilled, onRejected) {
        // 返回一个新的Promise，以便支持链式调用
        return new MyPromise((resolve, reject) => {
            // 处理成功回调函数
            const handleFulfilled = (value) => {
                try {
                    if (typeof onFulfilled === 'function') {
                        // 调用成功回调函数，并获取返回值
                        const result = onFulfilled(value);
                        // 将返回值传递给新的promise的resolve方法
                        resolve(result);
                    } else {
                        // 如果成功回调函数不是函数，直接传递值
                        resolve(value);
                    }
                } catch (error) {
                    // 如果成功回调函数抛出错误，调用新的Promise的reject方法
                    reject(error);
                }
            };
            // 处理失败回调函数
            const handleRejected = (reason) => {
                try {
                    if (typeof onRejected === 'function') {
                        // 调用失败回调函数，并获取返回值
                        const result = onRejected(reason);
                        // 将返回值传递给新的Promise的resolve方法
                        resolve(result);
                    } else {
                        // 如果失败回调函数不是函数，直接传递错误
                        reject(reason);
                    }
                } catch (error) {
                    // 如果失败回调函数抛出错误，调用新的promise的reject方法
                    reject(error);
                }
            };
            // 根据当前promise的状态执行相应的回调函数
            if (this.state === 'fulfilled') {
                // 如果当前promise状态为fulfilled，异步执行成功回调函数
                setTimeout(() => handleFulfilled(this.value), 0)
            } else if (this.state === 'rejected') {
                // 如果当前promise状态为rejected，异步执行失败回调函数
                setTimeout(() => handleRejected(this.value), 0)
            } else {
                // 如果当前promise状态为pending。将回调函数存储起来
                this.onFulfilledCallbacks.push(handleFulfilled)
                this.onRejectedCallbacks.push(handleRejected)
            }
        })
    }
}

实现all

  • 接收一个Promise数组，数组中如有非Promise项，则此项当作成功
  • 如果所有promise都成功，则返回成功结果数组
  • 如果有一个promise失败，第一个被reject的值则返回这个失败结果
js
function myPromiseAll(promises) {
    if (!Array.isArray(promises)) {
        throw new Error('params must be a Array')
    }
    let results = [];
    let count = 0;
    return new Promise((resolve, reject) => {
        // 处理空数组情况
        if(promises.length === 0) {
            resolve(results);
            return;
        }
        promises.forEach((promise, index) => {
            // 将每个promise转换为promise对象
            Promise.resolve(promise)
                .then(result => {
                    // 将结果按顺序存入results数组
                    results[index] = result;
                    count++;
                    // 如果所有promise都已完成，则resolve
                    if(count === promise.length) {
                        resolve(results);
                    }
                })
                .catch(error => {
                    // 如果任何一个promise被拒绝，则reject
                    reject(error);
                })
        })
    })
}

    if (!Array.isArray(promises)) {
        throw new Error('params must be a Array')
    }
    return new Promise((resolve, reject) => {
        const results = [];
        let completedCount = 0;
        if(promises.length === 0) {
            resolve(results);
            return;
        }
        promises.forEach((promise, index) => {
            // 将每个promise转换为promise对象
            Promise.resolve(promise)
                .then(
                value => {
                   results[index] = { status: 'fulfilled', value };
                },
                reason => {
                    results[index] = { status: 'rejected', reason }
                }
                )
                .finally(() => {
                    completedCount++;
                    if(completedCount === promises.length) {
                        resolve(results);
                    }
                })
        })
    })
}

finally Promise 的工作原理以及如何在promise链中处理成功和失败的情况，finally方法会在promise链中的任何地方被调用，无论promise是成功还是失败

js
Promise.prototype.finally = function(callback) {
    // 获取当前 promise实例
    const promise = this;
    // 返回一个新的promise，确保finally方法可以链式调用
    return promise.then(
        // 如果promise成功，调用callback并传递结果
        value => Promise.resolve(callback()).then(()=>value),
        // 如果promise失败，调用callback并传递错误
        reason => Promise.reolve(callback()).then(()=>{ throw reason })
    )
}

防抖和节流 ​

防抖（Debounce）:事件停止触发后延迟执行，期间再次触发重新计时

js
function debounce(fn, delay){
    let timer = null;
    return function (...args){
        clearTimeout(timer);
        timer = setTimeout(() => fu.apply(this, args), delay);
    };
}

节流（Throttle）:固定时间间隔执行，期间多次触发只执行一次

js
function throttle(fn, limit){
    let inThrottle = false;
    return function (...args){
        if(!inThrottle){
            fn.apply(this, args);
            inThrottle = true;
            setTimeout(() => inThrottle = false, limit)
        }
    }
}

        for (var j =0; j < len - 1; j++){

        }

function quickSort(arr) {
    if(arr.length<=1) return arr;
    const pivotIndex = Math.floor(arr.length/2)
    const pivot = arr[pivotIndex]
    let left = []
    let right = []

    for (let i = 0; i < arr.length; i++){
        if(i === pivotIndex) continue
        if(arr[i] < pivot){
            left.push(arr[i])
        } else {
            right.push(arr[i])
        }
    }
    return [...quickSort(left),pivot,...quickSort(right)]
}

当用户在浏览器url输入一个域名后的过程 ​

  1. DNS 域名解析

    md
    首先域名进行DNS解析，
1. 浏览器DNS缓存查询。
2. 操作系统DNS缓存查询
3. 本地DNS服务器查询
4. 根DNS服务器迭代查询
最终把IP地址返回给浏览器。

  2. 建立 TCP 连接

    md
    浏览器拿到IP地址后，与服务器建立TCP连接，使用三次握手。
1. 第一次握手：客户端发送SYN包（seq=x），进行SYN_SENT状态
2. 第二次握手：服务端返回SYN+ACK包（ack=x+1，seq=y），进行SYN_RCVD状态
3. 第三次握手：客户端发送ACK包（ack=x+1），双方进入ESTABLISHED状态

补充：
为什么三次握手？
两次握手无法可靠地同步双方的初始化序号，
也无法防止已失效的连接请求导致服务器单方面建立连接，
这既浪费资源又存在安全隐患。

  3. HTTPS TLS 握手

    md
    如果是HTTPS协议，在TCP连接建立后，还需要进行TLS握手。
1. 客户端Hello：发送支持的TLS版本、加密套件、随机数Client Random
2. 服务器Hello：确认TLS版本、选择加密套件、返回随机数Server Random
3. 服务器证书：发送数字证书（包含公钥），客户端验证证书合法性
4. 密钥交换：客户端生成Pre-Master Secret，用服务器公钥加密后发送
5. 会话密钥生成：双方用Client Random + Server Random + Pre-Master Secret 生成相同的会话密钥
6. 握手完成：双方发送Finished消息，后续所有通信使用会话密钥加密

  4. 发送HTTP请求

    md
    连接建立后，浏览器构造并发送 HTTP 请求报文：
1. 请求报文结构
    - 请求行：GET /index.html HTTP/1.1
    - 请求头：Host、User-Agent、Accept、Cookie、Connection等
    - 空行
    - 请求体：（仅POST/PUT等方法有）
2. 浏览器缓存检查
    - 强缓存：检查Expires和Cache-Control，若未过期，直接从本地缓存读取，不发请求
    - 协商缓存：若强缓存失效，发送请求携带If-Modified-Since/If-None-Match
    - 服务器返回304 Not Modified，浏览器使用本地缓存；返回200则使用新资源
3. 请求发送
    - HTTP/1.1:是串行传输，队头阻塞严重
    - HTTP/2:通过单连接多路复用解决了 HTTP 层的阻塞，但 TCP 层的阻塞还在；
    - HTTP/3:直接换了 UDP 加 QUIC，在传输层也独立了，真正实现了非阻塞的多路复用，延迟更低、连接更稳。

    补充： 首先是 HTTP/1.1。 它基于 TCP，一个连接上请求必须串行处理。虽然浏览器会开 6~8 个并行连接，但每个连接内部还是有严重的队头阻塞，一个请求卡住，后面的全卡住。为了优化它，前端不得不做雪碧图、域名分片、资源内联这些操作。 再到 HTTP/2。 它最大的改进是引入了二进制分帧和多路复用，在一个 TCP 连接上可以同时传输多个请求响应流，互相独立，不再需要域名分片了。同时还有头部压缩（HPACK）和服务器推送的能力。 但是，因为它的底层还是 TCP，如果 TCP 发生丢包，所有流都会被阻塞，这叫 TCP 层的队头阻塞，这是 HTTP/2 的致命弱点。 接着是 HTTP/3。 它把传输层从 TCP 换成了 UDP + QUIC 协议，彻底解决了这个问题。QUIC 里每个流在传输层就是独立的，一个流丢包只影响它自己，其他流不阻塞。而且 QUIC 在一个握手内集成了 TLS 1.3，可以做到 0-RTT 或 1-RTT 建连，延迟很低。 还有一个很实用的特性是 连接迁移，手机切换 4G/WiFi 时，连接不会断，因为 QUIC 不再依赖 IP，而是用连接 ID 来跟踪会话。

  5. 服务器处理请求与响应

    md
    
1. 服务器接收请求
    - 反向代理（Nginx）接收请求，根据配置转发到对应的应用服务器
    - 负载均衡：将请求分发到多个应用服务器实例
2. 应用服务器处理
    - 路由解析：根据 URL 路径匹配对应的处理函数
    - 业务逻辑处理：查询数据库、调用接口、生成动态内容
    - 模板渲染：将数据填充到 HTML 模板中
3. 返回 HTTP 响应

常见状态码（面试必问）：
    2xx：成功（200 OK、206 Partial Content）
    3xx：重定向（301 永久重定向、302 临时重定向、304 未修改）
    4xx：客户端错误（400 请求错误、401 未授权、403 禁止访问、404 未找到）
    5xx：服务器错误（500 内部服务器错误、502 网关错误、503 服务不可用）

  6. 浏览器解析渲染页面

    md
    
1. 解析 HTML 生成 DOM 树
    - 逐行解析 HTML 文档，遇到标签生成对应的 DOM 节点
    - 遇到`<script>`标签会阻塞 HTML 解析和后续渲染（因为 JS 可能修改 DOM）
    - 解决：defer（延迟执行，DOM 解析完成后按顺序执行）、async（异步执行，下载完成后立即执行，不保证顺序）
    - 遇到`<link rel="stylesheet">`不会阻塞 HTML 解析，但会阻塞渲染
2. 解析 CSS 生成 CSSOM 树
    - 解析 CSS 文件和`<style>`标签内的样式
    - 计算每个 DOM 节点的最终样式（层叠、继承、优先级计算）
    - CSS 选择器匹配从右往左进行，提高匹配效率
3. 生成渲染树（Render Tree）
    - 将 DOM 树和 CSSOM 树结合，生成只包含可见节点的渲染树
    - display: none的节点不会出现在渲染树中
    - visibility: hidden的节点会出现在渲染树中（占据空间）
4. 布局（Layout/Reflow 重排）
    - 计算渲染树中每个节点的精确位置和大小
    - 这是一个递归过程，从根节点开始，依次计算子节点
    - 重排非常消耗性能，应尽量避免
5. 绘制（Paint/Repaint 重绘）
    - 根据布局结果，将每个节点绘制到屏幕上
    - 绘制过程分为多个层（Layer），提高渲染效率
    - 重绘比重排性能消耗小，但仍需优化
6. 合成（Composite）
    - 将多个层合并成最终的屏幕图像
    - 由 GPU 加速完成，性能最好
    - transform和opacity属性只会触发合成，不会触发重排和重绘

重排与重绘的区别及优化
    重排：元素的几何属性（位置、大小）发生变化，需要重新计算布局
    重绘：元素的样式（颜色、背景）发生变化，不需要重新计算布局
优化方法：
    批量修改 DOM（使用 DocumentFragment）
    避免频繁读取布局属性（浏览器会批量处理重排，读取属性会强制刷新）
    使用transform和opacity做动画
    开启 GPU 加速（will-change: transform）
    减少 DOM 层级

  7. 资源加载与页面交互

    md
    1. 解析过程中并行加载图片、字体等资源，加载优先级大致为 HTML > CSS > JS > 图片/字体。
2. JS 完成后执行（除非有 defer/async），会阻塞 DOM 构建和渲染。
3. 页面关键事件： DOMContentLoaded（DOM 就绪）、load（全部资源就绪）

  8. TCP 连接关闭

    md
    
1. 数据传输完成后，通过四次挥手关闭 TCP 连接：
    1. 第一次挥手：客户端发送FIN包（seq=m），进入FIN_WAIT_1状态
    2. 第二次挥手：服务器返回ACK包（ack=m+1），进入CLOSE_WAIT状态
    3. 第三次挥手：服务器发送FIN包（seq=n），进入LAST_ACK状态
    4. 第四次挥手：客户端返回ACK包（ack=n+1），进入TIME_WAIT状态，等待 2MSL 后关闭连接

    补充：为什么是四次挥手？ 因为 TCP 是全双工通信，双方都需要独立关闭自己的发送通道。服务器收到客户端的 FIN 后，可能还有数据要发送，所以先回复 ACK，等数据发送完再发送 FIN。

Vue3.0 性能提升主要是通过哪几方面体现的？ ​

Vue3.0的性能提升主要体现在编译阶段优化、源码体积优化和响应式系统重写三个核心方面。

在编译阶段，Vue3做了多项针对性优化。首先是diff算法优化，引入了静态标记机制，会为动态节点添加对应的PatchFlag标记，更新时只对比有标记的动态部分，跳过所有静态节点的对比，大幅减少了diff的计算量。其次是静态提升，将不参与更新的静态节点和静态属性提升到渲染函数外部，只在首次渲染时创建一次，后续渲染直接复用，避免了重复创建节点的性能开销。然后是事件监听缓存，默认开启事件缓存，将事件处理函数缓存起来，不再视为动态绑定，每次渲染时不需要重新追踪和绑定事件。最后是SSR优化，当静态内容达到一定量级时，会直接生成静态HTML字符串，不需要创建虚拟DOM对象再渲染，显著提升了服务端渲染的速度。

在源码体积方面，Vue3相比Vue2整体体积更小。一方面移除了一些不常用的API，另一方面全面支持Tree Shaking，任何未被使用的功能模块都会被打包工具摇掉，只有实际用到的函数如ref、reactive、computed等才会被打包进最终产物，有效减小了应用的打包体积。

在响应式系统方面，Vue3用ES6的Proxy完全重写了响应式实现，替代了Vue2的Object.defineProperty。Proxy可以直接监听整个对象，不需要像Vue2那样深度遍历所有属性添加getter和setter，同时解决了Vue2无法监听动态添加的属性、数组的索引和length属性变化，以及属性删除操作的问题，不仅提升了响应式的性能，还完善了响应式的功能覆盖。

Vue组件间通信方式 ​

面试官您好，Vue组件间通信的本质是解决不同组件独立作用域下的数据共享与状态同步问题，根据组件关系不同，主要有8种主流方案，我按优先级和适用场景给您介绍：

首先是最常用的父子组件通信：父传子用Props，支持类型校验、默认值和必填校验，遵循严格的单向数据流；子传父用$emit触发自定义事件，子组件携带参数，父组件通过@绑定监听。另外父组件也可以用ref直接获取子组件的实例，调用它的方法或访问属性。

然后是祖孙/跨代通信：首选Provide/Inject依赖注入，祖先组件提供数据或方法，任意层级的后代组件都能直接注入接收，注意它默认是非响应式的，传入ref或reactive对象就能实现响应式。还有$attrs和$listeners可以批量透传属性和事件，不用逐层声明props，适合封装高阶组件。

接下来是兄弟和非关系组件：小型项目的简单场景可以用EventBus事件总线，基于发布订阅模式实现；中大型项目统一用Pinia（Vue3官方推荐）或Vuex做全局状态管理，把共享状态抽离到store统一维护，解决复杂的跨组件状态同步。

最后还有$parent和$root可以通过共同祖先中转通信，但耦合度高，代码可维护性差，不推荐大规模使用。

总结一下选型原则：简单父子用Props/$emit，跨代用Provide/Inject，全局复杂状态用Pinia，小型项目轻量跨组件用mitt（Vue3替代EventBus）。

一、什么是虚拟DOM

虚拟 DOM （Virtual DOM ）这个概念相信大家都不陌生，从 React 到 Vue ，虚拟 DOM 为这两个框架都带来了跨平台的能力（React-Native 和 Weex）

创建虚拟DOM就是为了更好将虚拟的节点渲染到页面视图中，所以虚拟DOM对象的节点与真实DOM的属性一一照应

在vue中同样使用到了虚拟DOM技术

DOM是很慢的，其元素非常庞大，页面的性能问题，大部分都是由DOM操作引起的

操作DOM的代价仍旧是昂贵的，频繁操作还是会出现页面卡顿，影响用户的体验

很多人认为虚拟 DOM 最大的优势是 diff 算法，减少 JavaScript 操作真实 DOM 的带来的性能消耗。虽然这一个虚拟 DOM 带来的一个优势，但并不是全部。虚拟 DOM 最大的优势在于抽象了原本的渲染过程，实现了跨平台的能力，而不仅仅局限于浏览器的 DOM，可以是安卓和 IOS 的原生组件，可以是近期很火热的小程序，也可以是各种GUI

Vue中的 v-show 和 v-if 有什么区别 ​

参考答案：

v-if 和 v-show 是 Vue.js 中用于条件渲染的指令，它们的作用是根据条件来控制元素的显示和隐藏。它们之间有一些重要的区别：

  1. 编译时刻 vs 运行时刻：

    • v-if 是一个“惰性”指令，在编译时刻，Vue.js 会根据条件决定是否编译或挂载元素到 DOM 中。如果条件为 false，元素根本不会被编译和渲染到 DOM 中。

    • v-show 是一个“非惰性”指令，在编译时刻，元素总是会被编译和渲染到 DOM 中。但是，根据条件的值，v-show 会通过 CSS 控制元素的显示和隐藏，不会从 DOM 中移除元素。

  2. 显示隐藏方式：

    • v-if 在条件为 true 时会渲染元素到 DOM，而在条件为 false 时会从 DOM 中移除元素。v-if也可以触发组件创建和销毁的生命钩子。

    • v-show 在条件为 true 时会通过 CSS 设置元素的 display 属性为可见（通常是 display: block），在条件为 false 时设置为隐藏（display: none）。元素始终存在于 DOM 中，只是通过 CSS 控制其显示状态。

  3. 切换开销：

    • v-if 在条件切换时，如果条件从 true 切换为 false，会销毁并重新创建元素，这涉及到 DOM 的删除和重新插入，可能会有一定的性能开销。

    • v-show 在条件切换时，只是简单地通过 CSS 控制元素的显示和隐藏，不会销毁和重新创建元素，因此切换的开销较小。

  4. 初始渲染开销：

    • v-if 在初始渲染时，如果条件为 false，元素不会被渲染到 DOM 中，因此在初始渲染时可能会有一定的性能优势。

    • v-show 在初始渲染时，元素总是会被渲染到 DOM 中，因此在初始渲染时可能会有一些额外的开销。

综上所述，当需要频繁切换元素的显示状态时，且元素可能处于不同的状态，推荐使用 v-show。而当条件不会频繁改变，且希望在条件为 false 时不渲染元素到 DOM 中，推荐使用 v-if。在实际使用中，根据具体的场景和性能需求来选择合适的指令。

Vue3.0里为什么要用 Proxy API 替代 defineProperty API ？ ​

参考答案：

在 Vue 3.0 中，使用 Proxy API 替代 defineProperty API 是为了改进响应式系统的性能和功能：

  1. 性能提升：Proxy API 比 defineProperty API 在许多情况下具有更好的性能。defineProperty 使用 Object.defineProperty 方法来拦截对象属性的访问和修改，但它需要遍历每个属性进行拦截。而 Proxy API 允许拦截整个对象，可以更高效地捕获对对象的访问和修改。

  2. 更全面的拦截能力：Proxy API 提供了更多的拦截方法，比 defineProperty API 更灵活、丰富。它支持拦截目标的各种操作，包括读取、设置、删除、枚举等，甚至还可以拦截函数调用和构造函数实例化。

  3. 更好的数组变化检测：Vue 3.0 使用 Proxy API 改善了数组的变化检测机制。Proxy 可以直接拦截数组的索引访问和修改，使得对数组的变化更容易被监听到，从而提供了更可靠的响应式行为。

  4. 更易于处理嵌套对象：Proxy API 能够递归地拦截对象的嵌套属性，而 defineProperty 无法自动递归处理嵌套对象。这使得在 Vue 3.0 中处理嵌套对象更加简单和方便。

  5. 更好的错误提示：相比于 defineProperty，Proxy API 提供了更好的错误追踪和调试信息。当使用 Proxy API 时，如果访问或修改了一个不存在的属性，会直接抛出错误，从而更容易发现和修复问题。

使用 Proxy API 取代 defineProperty API 是为了提升性能、增强功能，并提供更好的开发体验和错误提示。这些改进使得 Vue 3.0 的响应式系统更加高效、灵活和可靠。

Scoped Styles 为什么可以实现样式隔离？ ​

参考答案：

在 Vue 中，作用域样式（Scoped Styles）是通过以下原理实现的：

  1. 唯一选择器：

    • 当 Vue 编译单文件组件时，在样式中使用 scoped 特性或 module 特性时，Vue 会为每个样式选择器生成一个唯一的属性选择器。

    • 这里的唯一选择器是类似于 [data-v-xxxxxxx] 的属性选择器，其中 xxxxxxx 是一个唯一的标识符。

  2. 编译时转换：

    • Vue 在编译过程中会解析单文件组件的模板，并对样式进行处理。

    • 对于具有 scoped 特性的样式，Vue 会将选择器转换为带有唯一属性选择器的形式，例如 .class 会被转换为 .class[data-v-xxxxxxx]。

    • 对于具有 module 特性的样式，Vue 会为每个选择器生成一个唯一的类名，并将类名与元素关联起来。

  3. 渲染时应用：

    • 在组件渲染过程中，Vue 会为组件的根元素添加一个属性值为唯一标识符的属性，例如 data-v-xxxxxxx。

    • 当组件渲染完成后，样式选择器中的唯一属性选择器或唯一类名将与组件根元素的属性匹配，从而实现样式的隔离。

    • 这样，只有具有相同属性值的元素才会应用相应的样式，避免了样式冲突和泄漏。

通过以上原理，Vue 实现了作用域样式的隔离。每个组件的样式都被限制在自己的作用域内，不会影响其他组件或全局样式。这种方式实现了组件级别的样式隔离，使得组件可以更好地封装和重用，同时减少了样式冲突的可能性。

created 和 mounted 有什么区别？ ​

参考答案：

在Vue中，created和mounted是两个常用的生命周期钩子函数，它们在组件的生命周期中扮演着不同的角色：

created：

  • created是组件生命周期中的一个钩子函数，在Vue实例被创建后立即调用。

  • 在created钩子函数中，Vue实例已经完成了数据观测（data observation），但尚未渲染真实DOM。这意味着你可以访问实例中的数据、方法、计算属性等，但不能保证实例已经被插入到DOM中。

  • created常用于一些初始化操作，例如数据请求、事件监听或其他非DOM相关的任务。因为此时，组件的模板还未被编译成真实DOM。

mounted：

  • mounted是组件生命周期中的一个钩子函数，在Vue实例挂载到DOM后调用。

  • 在mounted钩子函数中，Vue实例已经完成了模板编译，并且已经将生成的虚拟DOM渲染到真实DOM中。

  • mounted常用于需要对DOM进行操作的任务，例如初始化第三方库、绑定事件监听器、执行动画等。因为此时，组件已经被插入到DOM中，可以安全地访问和操作DOM元素。

区别总结：

  • created在实例创建后被调用，适合处理数据初始化和非DOM相关的任务。

  • mounted在实例挂载到DOM后被调用，适合进行DOM操作、初始化第三方库和绑定事件监听。

Vue是怎么把template模版编译成render函数的？ ​

参考答案：

Vue的编译过程将模板转换为渲染函数，这是Vue在运行时动态编译和渲染组件的关键步骤。下面是Vue将模板编译成渲染函数的大致过程：

  1. 解析模板：首先，Vue会解析模板字符串，将其转化为抽象语法树（AST）。AST是一个表示模板结构和内容的树状数据结构。

  2. 优化AST：接下来，Vue会对AST进行优化处理，以提升渲染性能。这包括标记静态节点、静态属性和静态文本等。

  3. 生成渲染函数：利用优化后的AST，Vue会生成渲染函数。渲染函数是一个JavaScript函数，它接收一个上下文对象作为参数，并返回一个虚拟DOM树（VNode）。

  4. 渲染虚拟DOM：当执行渲染函数时，它将生成一个新的虚拟DOM树。如果之前已经存在真实的DOM树，Vue将通过比较新旧VNode来计算最小的更新操作并应用在真实DOM上，从而进行局部更新，提高效率。

  5. 生成DOM：最后，Vue将根据最新的VNode生成真实的DOM元素，并将其插入到页面中，完成渲染。

Vue的编译过程通常在构建时（比如使用Vue CLI）或运行时的初始阶段完成，以便在实际渲染组件时获得更好的性能。这样一来，渲染函数会被缓存并重复使用，而不需要每次重新编译模板。

Vue还可以使用render函数直接编写组件而不依赖于模板。这种情况下，手动编写的render函数会跳过模板解析和优化的步骤，直接生成渲染函数并进行渲染。这种方式可以在需要更高级别的动态和灵活性时使用。

v-model 的原理是什么样的？ ​

参考答案：

v-model是Vue.js框架中的一个指令，用于在表单元素和组件之间实现双向数据绑定。它提供了一种简洁的方式来将表单输入的值与Vue实例的属性进行关联。

当使用v-model指令时，Vue会根据表单元素的类型（如input、select、textarea等）自动为其添加相应的事件监听器，并在用户输入时更新绑定的数据。

具体地讲，v-model的原理如下：

  1. 在模板中，我们可以使用v-model指令来绑定一个变量到表单元素（或组件）上，例如：<input v-model="message">。

  2. Vue解析模板时，会将v-model指令转换成合适的属性和事件绑定。对于大多数表单元素，它会将value属性与输入框的当前值进行绑定，并监听input事件来实时更新绑定的数据。

  3. 当用户在输入框中键入或选择内容时，触发input事件。Vue会捕获该事件并更新绑定的数据，以及根据数据的变化重新渲染视图。

  4. 同样地，如果在表单元素上使用v-model的lazy修饰符，Vue会监听change事件而不是input事件。这样，只有当用户完成输入并触发change事件时，才会更新绑定的数据。

v-model指令实现双向绑定的原理是通过监听表单元素的输入事件（如input或change），将用户的输入同步到Vue实例中的属性，并在属性值变化时重新渲染视图。这使得我们可以轻松地将表单数据与Vue实例的状态保持同步，消除了手动监听和更新的冗余代码。

说说vue中，key的原理 ​

参考答案：

在 Vue 中，key 是用于帮助 Vue 识别和跟踪虚拟 DOM 的变化的特殊属性。当 Vue 更新渲染真实 DOM 时，它使用 key 属性来比较新旧节点，并尽可能地复用已存在的真实 DOM 节点，以提高性能。

Vue 在进行虚拟 DOM 的 diff 算法时，会使用 key 来匹配新旧节点，以确定节点的更新、移动或删除。它通过 key 属性来判断两个节点是否代表相同的实体，而不仅仅是根据它们的内容是否相同。这样可以保留节点的状态和避免不必要的 DOM 操作。

key 的工作原理如下：

  1. 当 Vue 更新渲染真实 DOM 时，它会对新旧节点进行比较，找出它们之间的差异。

  2. 如果两个节点具有相同的 key 值，则 Vue 认为它们是相同的节点，会尝试复用已存在的真实 DOM 节点。

  3. 如果节点具有不同的 key 值，Vue 会将其视为不同的节点，并进行适当的更新、移动或删除操作。

使用 key 可以提供更准确的节点识别和跟踪，避免出现一些常见的问题，比如在列表中重新排序时导致的元素闪烁、输入框内容丢失等。

key 必须是唯一且稳定的，最好使用具有唯一标识的值，例如使用数据的唯一 ID。同时，不推荐使用随机数作为 key，因为在每次更新时都会生成新的 key，导致所有节点都重新渲染，无法复用已有的节点，降低性能。

Vuex 与 Pinia 核心区别总结 ​

Pinia是Vue官方推出的新一代状态管理库，专为Vue3设计且兼容Vue2，现已完全替代Vuex成为官方推荐方案。两者的核心差异体现在设计理念、API设计、开发体验和性能等多个方面：

一、设计理念与架构 Vuex采用单一状态树加模块化的架构，所有状态集中在一个根store中，通过modules划分业务模块，模块默认共享命名空间，需要手动开启namespaced: true才能实现隔离。而Pinia采用去中心化的模块化架构，没有根store的概念，每个业务模块都是一个独立的store实例，天然具备命名空间隔离能力，无需额外配置，更符合Vue3 Composition API的设计思想。

二、核心API差异 Vuex的核心组成包括State、Getters、Mutations和Actions四部分，规定必须通过commit调用Mutations进行同步状态修改，异步操作只能在Actions中通过commit间接触发状态更新。Pinia则彻底移除了冗余的Mutations，只保留State、Getters和Actions三个部分，支持直接在Actions中修改状态，同步和异步操作都可以在同一个方法中完成，不需要额外的commit步骤。

在模块注册上，Vuex需要在根store中手动注册所有业务模块，而Pinia无需手动注册，只要导入对应的store函数即可直接使用，天然支持自动代码分割。访问方式上，Vuex需要通过this.$store或useStore()获取根store，再通过模块名访问子模块的状态和方法；Pinia则可以直接导入对应业务的store函数，调用后就能直接访问该模块的所有内容。

三、TypeScript支持 Vuex对TypeScript的支持较差，需要手动编写大量的类型声明文件，无法实现完整的类型推断，开发体验不佳。而Pinia完全使用TypeScript编写，天生支持完整的类型推断，不需要额外编写类型定义，IDE的代码提示和类型检查都非常完善。

四、开发体验 Vuex的语法相对繁琐，修改状态需要经过Actions到Mutations的两层调用，当模块嵌套过深时，状态的访问路径会很长，容易出错，同时热重载的配置也比较复杂。Pinia的语法简洁直观，直接修改状态的方式大幅减少了样板代码，整体代码量相比Vuex减少约30%；它完全支持Composition API风格，与Vue3组件的写法保持一致；开箱即用地支持热重载，不需要任何额外配置；还支持在组件外部直接使用store，不依赖Vue实例。

五、性能与体积 Pinia的体积更小，仅约1KB，并且全面支持Tree Shaking，未被使用的功能不会被打包进最终产物。Vuex的体积更大，且无法进行有效的Tree Shaking。性能方面，Pinia基于Vue3原生的响应式系统实现，状态更新的效率更高；Vuex4虽然适配了Vue3，但整体架构仍然保留了Vuex3的设计，存在一定的性能开销。

六、其他特性 Pinia拥有一些Vuex不具备的特性，包括支持多个store之间的相互引用，提供了更强大的插件系统，可以轻松实现状态持久化、日志记录、状态同步等功能，同时完整支持DevTools的时间旅行、状态快照等调试功能，也对SSR有良好的支持。Vuex独有的特性包括支持命名空间的深度嵌套，以及提供modules的动态注册功能，而Pinia不需要动态注册，直接导入对应的store即可使用。

总结与适用场景 对于所有新项目，无论使用Vue2还是Vue3，都强烈推荐使用Pinia，它拥有更好的开发体验、更完善的TypeScript支持和更优的性能。对于已经使用Vuex的旧项目，不需要强制进行迁移，Vuex4仍会继续维护，但新功能的开发建议逐步迁移到Pinia。本质上Pinia是Vuex的进化版本，它去掉了Vuex中冗余和反直觉的设计，简化了API的同时保留了状态管理的核心能力，更符合现代前端开发的需求。

Vue生命周期与Vue2/Vue3对比 ​

Vue生命周期是组件实例从创建到销毁的完整过程，Vue在不同阶段提供钩子函数执行自定义逻辑，所有钩子自动绑定this到实例，不能用箭头函数定义。

Vue2生命周期 分为4个核心阶段，共8个基础钩子：

  1. 创建阶段

    • beforeCreate：实例刚创建，无法访问data、methods
    • created：数据观测、方法配置完成，可访问修改数据、调用方法，DOM未生成，是发起网络请求的最佳时机

  2. 挂载阶段

    • beforeMount：模板编译完成，$el已初始化但未挂载到页面
    • mounted：DOM挂载渲染完成，可执行DOM操作、初始化第三方插件

  3. 更新阶段

    • beforeUpdate：数据已更新，视图未同步
    • updated：视图更新完成，修改数据会再次触发更新，需避免无限循环

  4. 销毁阶段

    • beforeDestroy：实例即将销毁，属性方法仍可用，用于清理定时器、取消订阅等副作用
    • destroyed：实例完全销毁，所有事件监听器已解绑

特殊钩子：activated/deactivated（keep-alive缓存组件激活/失活）、errorCaptured（捕获子孙组件错误）

Vue3生命周期变化

  1. 选项式API：仅销毁阶段钩子改名，语义更清晰

    • beforeDestroy → beforeUnmount
    • destroyed → unmounted 其余钩子名称和调用时机与Vue2完全一致

  2. 组合式API（setup）：

    • 无beforeCreate和created，setup本身替代这两个钩子
    • 其余钩子对应为onXxx形式，需从vue导入后在setup内调用： onBeforeMount、onMounted、onBeforeUpdate、onUpdated、onBeforeUnmount、onUnmounted
    • 特殊钩子对应：onActivated、onDeactivated、onErrorCaptured
    • 新增调试钩子：onRenderTracked（响应式数据被追踪时）、onRenderTriggered（触发渲染时）
    • 支持同一组件多次调用同一个钩子，便于逻辑拆分

核心差异

  • 初始化：Vue2用beforeCreate+created，Vue3用setup统一处理
  • 组合式API支持逻辑拆分复用，更适合大型项目
  • Vue3新增调试钩子，提升响应式问题排查效率

数据请求时机 建议在created（Vue2）或setup（Vue3）中发起，更早完成避免页面闪动；若依赖DOM节点则放在mounted/onMounted中。

我们知道 computed 内定义的 function 只执行一次，仅当初始化显示或者相关的 data、props 等属性数据发生变化的时候调用；

而 computed 属性值默认会缓存计算结果，计算属性是基于它们的响应式依赖进行缓存的；

只有当 computed 属性被使用后，才会执行 computed 的代码，在重复的调用中，只要依赖数据不变，直接取缓存中的计算结果。只有依赖型数据发生改变，computed 才会重新计算。

计算属性的高级：

在computed 中的属性都有一个 get 和一个 set 方法，当数据变化时，调用 set 方法。下面我们通过计算属性的 getter/setter 方法来实现对属性数据的显示和监视，即双向绑定。

watch 监听属性

通过 vm 对象的 $watch() 或 watch 配置来监听 Vue 实例上的属性变化，或某些特定数据的变化，然后执行某些具体的业务逻辑操作。当属性变化时，回调函数自动调用，在函数内部进行计算。其可以监听的数据来源：data，props，computed 内的数据。

注： 监听函数有两个参数，第一个参数是最新的值，第二个参数是输入之前的值，顺序一定是新值，旧值，如果只写一个参数，那就是最新属性值。

在使用时选择 watch 还是 computed，还有一个参考点就是官网说的：当需要在数据变化时执行异步或开销较大的操作时，watch方式是最有用的。所以 watch 一定是支持异步的。

上面仅限监听简单数据类型，监听复杂数据类型就需要用到深度监听 deep。

deep：为了发现对象内部值的变化，可以在选项参数中指定 deep: true。注意监听数组的变更不需要这么做。

若果要监听对象的单个属性的变化，有两种方法：

  1. 直接监听对象的属性
  • 与 computed 属性配合使用，computed 返回想要监听的属性值，watch 用来监听

总结：

watch和computed都是以Vue的依赖追踪机制为基础的，当某一个依赖型数据（依赖型数据：简单理解即放在 data 等对象下的实例数据）发生变化的时候，所有依赖这个数据的相关数据会自动发生变化，即自动调用相关的函数，来实现数据的变动。

当依赖的值变化时，在watch中，是可以做一些复杂的操作的，而computed中的依赖，仅仅是一个值依赖于另一个值，是值上的依赖。

应用场景：

computed：用于处理复杂的逻辑运算；一个数据受一个或多个数据影响；用来处理watch和methods无法处理的，或处理起来不方便的情况。例如处理模板中的复杂表达式、购物车里面的商品数量和总金额之间的变化关系等。

watch：用来处理当一个属性发生变化时，需要执行某些具体的业务逻辑操作，或要在数据变化时执行异步或开销较大的操作；一个数据改变影响多个数据。例如用来监控路由、inpurt 输入框值的特殊处理等。

区别：

computed

  • 初始化显示或者相关的 data、props 等属性数据发生变化的时候调用；

  • 计算属性不在 data 中，它是基于data 或 props 中的数据通过计算得到的一个新值，这个新值根据已知值的变化而变化；

  • 在 computed 属性对象中定义计算属性的方法，和取data对象里的数据属性一样，以属性访问的形式调用；

  • 如果 computed 属性值是函数，那么默认会走 get 方法，必须要有一个返回值，函数的返回值就是属性的属性值；

  • computed 属性值默认会缓存计算结果，在重复的调用中，只要依赖数据不变，直接取缓存中的计算结果，只有依赖型数据发生改变，computed 才会重新计算；

  • 在computed中的，属性都有一个 get 和一个 set 方法，当数据变化时，调用 set 方法。

watch

  • 主要用来监听某些特定数据的变化，从而进行某些具体的业务逻辑操作，可以看作是 computed 和 methods 的结合体；

  • 可以监听的数据来源：data，props，computed内的数据；

  • watch支持异步；

  • 不支持缓存，监听的数据改变，直接会触发相应的操作；

  • 监听函数有两个参数，第一个参数是最新的值，第二个参数是输入之前的值，顺序一定是新值，旧值。

一、是什么

Tree shaking 是一种通过清除多余代码方式来优化项目打包体积的技术，专业术语叫 Dead code elimination

简单来讲，就是在保持代码运行结果不变的前提下，去除无用的代码

如果把代码打包比作制作蛋糕，传统的方式是把鸡蛋（带壳）全部丢进去搅拌，然后放入烤箱，最后把（没有用的）蛋壳全部挑选并剔除出去

而treeshaking则是一开始就把有用的蛋白蛋黄（import）放入搅拌，最后直接作出蛋糕

也就是说 ，tree shaking 其实是找出使用的代码

怎么设计通用型组件、怎么二次封装组件 ​

通用组件的核心是高内聚、低耦合、可复用、可扩展，二次封装则是在现有组件（原生或第三方）基础上，根据业务需求进行抽象和增强，减少重复代码。整个过程分为三个核心步骤：

一、确认动机：明确为什么要封装

封装前必须先判断是否有必要，避免过度封装。核心动机包括：

  1. 减少重复代码：当多个页面出现相同或高度相似的UI和逻辑时，提取为通用组件
  2. 统一视觉与交互规范：封装基础组件（按钮、表单、弹窗等），保证全项目风格一致
  3. 降低页面复杂度：将复杂的业务逻辑和UI结构封装在组件内部，页面只关注业务流程
  4. 便于维护与迭代：修改一处即可同步所有使用位置，避免多处修改导致的不一致
  5. 隔离第三方依赖：二次封装第三方组件，降低项目与特定库的耦合度，方便后续替换

二、分析边界：明确组件的职责与范围 这是最关键的一步，边界不清会导致组件过于臃肿或灵活性不足。

  1. 遵循单一职责原则 一个组件只负责一件事，避免"万能组件"。例如：

    • 不要在一个表格组件里同时封装分页、搜索、增删改查逻辑
    • 应该拆分为基础表格组件、分页组件、搜索组件，再组合使用

  2. 区分内部状态与外部状态

    • 内部状态：组件自身控制、外部不需要关心的状态，如弹窗的显示/隐藏、输入框的聚焦状态
    • 外部状态：由父组件控制、影响组件行为的状态，如表单的提交数据、表格的数据源
    • 原则：能通过外部控制的状态尽量不要放在组件内部，提升组件的可控性

  3. 确定组件的输入与输出

    • 输入：组件需要接收哪些props，哪些是必填的，哪些是可选的
    • 输出：组件需要向父组件触发哪些事件，返回哪些数据
    • 避免：组件内部直接修改父组件传入的props，所有状态变更都通过事件通知父组件

  4. 预留扩展点 考虑未来可能的需求变化，预留插槽和自定义配置，避免频繁修改组件核心代码。例如：

    • 表格组件预留表头、单元格、操作栏的插槽
    • 按钮组件预留自定义图标、加载状态的配置

  5. 明确兼容性要求

    • 是否需要支持v-model双向绑定
    • 是否需要透传原生HTML属性和事件
    • 是否需要适配不同的尺寸、主题、语言

三、设计接口：定义清晰易用的组件API 好的API应该直观、一致、符合直觉，让使用者不需要看文档就能快速上手。

1. Props设计 ​

  • 命名规范：使用驼峰命名法，语义化清晰，避免缩写。例如：placeholder而不是ph，disabled而不是isDisabled
  • 类型校验：使用TypeScript或Vue的props类型校验，明确每个prop的类型、默认值和是否必填
  • 合理的默认值：为非必填prop提供符合大多数场景的默认值，减少使用成本
  • 避免过多的布尔值：当有多个互斥的状态时，使用枚举类型代替多个布尔值。例如：type="primary"而不是primary: true
  • 扁平化结构：尽量使用扁平的props结构，避免嵌套过深的对象，便于传递和修改

2. 事件设计 ​

  • 命名规范：使用动词开头，语义化清晰，避免和原生事件重名。例如：onSubmit、onClose、onSelectionChange
  • 统一的参数格式：事件回调的参数保持一致，通常第一个参数是事件相关的数据，第二个参数是原始事件对象
  • 避免过多的事件：将相关的事件合并，通过参数区分不同的行为。例如：用onAction(type, data)代替onAdd、onEdit、onDelete

3. 插槽设计 ​

  • 默认插槽：用于放置组件的主要内容，如按钮的文字、卡片的内容
  • 具名插槽：用于放置多个不同位置的内容，如弹窗的头部、底部
  • 作用域插槽：用于将组件内部的数据暴露给父组件，实现自定义渲染。例如：表格的单元格插槽，将当前行数据传递给父组件

4. 支持v-model ​

Vue3中支持多个v-model绑定，适合需要双向绑定的场景

5. 透传属性与事件 ​

使用v-bind="$attrs"和v-on="$listeners"（Vue2）或直接透传（Vue3），将未在props中声明的原生属性和事件透传给组件内部的根元素，保留原生组件的所有能力。

四、二次封装组件的特殊注意事项 二次封装第三方组件（如Element Plus、Ant Design Vue）时，除了遵循上述原则，还需要注意：

  1. 不要过度封装：保留原组件的核心API，不要为了"简化"而隐藏原组件的常用功能
  2. 透传所有原组件的props和事件：使用v-bind="$attrs"和v-on="$listeners"，避免手动转发每一个属性和事件
  3. 提供统一的默认配置：将项目中常用的配置设置为默认值，减少重复代码。例如：统一设置按钮的大小、表格的边框样式 扩展业务逻辑：在原组件基础上添加业务相关的逻辑，而不是修改原组件的行为。例如：在上传组件中添加文件类型校验、大小限制、上传进度显示
  4. 隔离第三方依赖：如果未来可能替换第三方组件，将所有与第三方相关的代码封装在组件内部，外部只使用封装后的API

五、最佳实践

  1. 保持组件纯粹：尽量编写纯函数组件，相同的props输入总是得到相同的输出，避免副作用
  2. 避免全局状态依赖：组件内部不要直接访问全局状态（如Vuex/Pinia），所有数据都通过props传入，提升组件的可移植性
  3. 完善的文档和示例：为组件编写清晰的使用文档，包括props、事件、插槽的说明，以及常见场景的示例代码
  4. 编写单元测试：为组件的核心功能编写单元测试，保证组件的稳定性和可靠性
  5. 渐进式封装：先满足当前需求，不要一开始就追求"大而全"，随着需求的迭代逐步完善组件的功能

项目登录流程怎么写的 ​

Vue项目的标准登录流程是一个完整的闭环，核心分为以下几个环节：

用户在登录页输入账号密码后，前端先进行基础的表单校验，包括非空、格式验证，同时显示加载状态防止重复提交。校验通过后调用后端登录接口，后端验证账号密码无误后返回token。前端将token同时存储在状态管理（Pinia/Vuex）和本地存储中，保证刷新页面状态不丢失，随后立即请求用户信息接口，将用户信息存入状态管理用于后续页面展示和权限判断，最后跳转到首页或用户之前被拦截的目标页面。

全局层面会配置两个核心拦截机制：一是Axios请求拦截器，自动为所有请求头携带token；响应拦截器统一处理错误，当检测到token过期（401状态码）时，自动清除登录状态并跳转到登录页。二是全局路由守卫，拦截所有路由跳转，访问需要权限的页面时检查是否存在有效token，无token则跳转到登录页并记录原跳转地址；已登录用户访问登录页则直接重定向到首页。

退出登录时，清除状态管理和本地存储中的token与用户信息，跳转回登录页即可。

为什么 react 需要 fiber 架构，而 Vue 却不需要？ ​

参考答案：

React引入Fiber架构的主要原因是为了实现更好的异步渲染和更高效的任务调度。Fiber架构使得React能够更细粒度地控制和中断渲染过程，以便更好地响应用户交互、实现懒加载等功能。Vue在设计上采用了不同的策略，因此并不需要类似于Fiber的架构。

以下是一些原因解释为什么React选择了Fiber架构，而Vue没有类似的架构：

  1. 异步渲染和任务优先级： React的Fiber架构使得实现异步渲染和任务优先级变得更加容易。这对于复杂的用户界面和大规模应用中的性能优化非常重要。React可以通过中断和恢复渲染过程，根据任务的优先级调度渲染工作，从而更好地响应用户输入和满足实时性要求。

  2. 更好的中断和恢复机制： Fiber架构提供了一种更灵活的中断和恢复机制，允许React在渲染过程中暂停、中断，然后根据优先级恢复。这使得React能够更好地处理复杂的渲染逻辑，并在需要时放弃低优先级的工作。

  3. 增量更新： Fiber允许React实现增量更新，即只更新变化的部分而不必重新渲染整个组件树。这对于提高渲染性能和减少不必要的工作非常有帮助。

Vue在设计上采用了一种不同的响应式系统和渲染机制，不需要像React那样进行复杂的中断和任务调度。Vue的设计目标可能更注重简洁性和开发体验，而React的目标之一是提供更灵活和强大的性能优化工具。每个框架在设计上都有权衡和取舍，选择适合其目标和使用场景的策略。

setState 是同步，还是异步的？ ​

React 18 及以上：所有场景下的 setState 都会触发自动批处理，统一表现为异步更新。 React 18 之前：仅在 React 控制的合成事件和生命周期钩子中表现为 "异步"（本质是代码同步执行，但更新被 React 批量延迟，导致无法立即获取最新 state）；在原生 DOM 事件、setTimeout/setInterval、Promise 回调等绕过 React 调度的场景中，setState 会同步更新 state。 无论哪个版本，setState 的 "异步" 都不是指内部有异步代码，而是 React 的批量更新机制导致的结果；获取更新后的值可通过 setState 的第二个回调参数或 useEffect 钩子实现。

React 合成事件与原生事件的执行顺序 ​

React 合成事件与原生事件的执行顺序以 17 版本为决定性分水岭：16 及更早将事件委托在全局 document，原生事件流走完到 document 冒泡阶段才统一执行所有合成事件；17 及以后委托在应用根节点，先执行合成捕获、再走完整原生事件流、最后执行合成冒泡，且合成事件的stopPropagation()能正常阻止原生事件向上冒泡。

React Fiber 是如何实现更新过程可控？ ​

核心背景：React 16之前的Stack Reconciler采用递归遍历虚拟DOM的方式，更新过程一旦开始就无法中断，长时间计算会阻塞浏览器主线程，导致页面卡顿、交互无响应。Fiber架构通过任务拆分、任务调度、优先级管理三大核心机制，实现了更新过程的完全可控。

1. 任务拆分：化整为零，将大任务拆分为原子单元

  • 以Fiber节点作为最小任务单元，每个DOM元素、组件都对应一个Fiber节点
  • 用链表结构（child指向子节点、sibling指向兄弟节点、return指向父节点）替代传统递归栈，使得遍历过程可以随时中断和恢复
  • 调和过程通过workLoop工作循环驱动，每次只处理一个Fiber节点，处理完后主动检查是否需要让出主线程

2. 任务调度：实现任务的挂起、恢复与终止

  • 双缓存树机制：维护两棵相互关联的Fiber树
    • current树：当前屏幕上显示内容对应的已提交状态
    • workInProgress树：正在构建中的新树，所有diff比较、副作用收集都在这棵树上进行
    • 两棵树的对应节点通过alternate指针相互指向，实现节点复用，减少内存开销
  • 时间切片技术：每处理完一个Fiber节点，检查当前浏览器帧是否有剩余时间
    • 有空闲：继续处理下一个节点
    • 无空闲：挂起任务并记录当前处理位置，让出主线程给浏览器处理渲染、用户输入等任务；下一帧有空闲时从断点恢复执行
  • 任务终止：若调和过程中触发了更高优先级的更新，立即终止当前低优先级任务，丢弃未完成的workInProgress树，重新开始高优先级更新（这也是React 16后componentWillMount等旧生命周期可能多次执行的根本原因）

3. 优先级管理：确保紧急任务优先响应

  • 为每个更新任务分配优先级：早期用expirationTime（过期时间越短优先级越高），React 18引入更精细的Lane模型支持多优先级并行调度
  • 调度器优先处理高优先级任务，已过期的任务无论当前帧是否有空闲时间都必须立即执行，避免任务饥饿
  • 调和阶段会收集所有需要执行的DOM操作、生命周期调用、ref更新等副作用，最终形成一条统一的副作用链表

关键补充： Fiber的可控性仅体现在调和阶段，提交阶段是同步且不可中断的。因为提交阶段会执行真实的DOM更新，中途中断会导致页面出现部分更新、状态不一致的视觉问题。提交阶段会一次性遍历完整的副作用链表，完成所有更新操作后，将workInProgress树替换为current树，整个更新过程结束。

简述下 React 的事件代理机制？ ​

参考答案：

React 并不会把所有的处理函数直接绑定在真实的节点上。而是把所有的事件绑定到结构的最外层，使用一个统一的事件监听器，这个事件监听器上维持了一个映射来保存所有组件内部的事件监听和处理函数。

当组件挂载或卸载时，只是在这个统一的事件监听器上插入或删除一些对象。

当事件发生时，首先被这个统一的事件监听器处理，然后在映射里找到真正的事件处理函数并调用。

这样做的优点是解决了兼容性问题，并且简化了事件处理和回收机制（不需要手动的解绑事件，React 已经在内部处理了）。但是有些事件 React 并没有实现，比如 window 的 resize 事件。

在React@17.0.3版本中：

  • 所有事件都是委托在id = root的DOM元素中（网上很多说是在document中，17版本不是了）；

  • 在应用中所有节点的事件监听其实都是在id = root的DOM元素中触发；

  • React自身实现了一套事件冒泡捕获机制；

  • React实现了合成事件SyntheticEvent；

  • React在17版本不再使用事件池了（网上很多说使用了对象池来管理合成事件对象的创建销毁，那是16版本及之前）；

  • 事件一旦在id = root的DOM元素中委托，其实是一直在触发的，只是没有绑定对应的回调函数；

之所以会将事件委托从document中移到id = root的DOM元素，是为了可以更加安全地进行新旧版本 React 树的嵌套。

  • getSnapshotBeforeUpdate() DOM 更新前调用，在 render 之后、commit 之前

  • componentDidUpdate() DOM 更新完成后立即调用

卸载

当组件从 DOM 中移除时会调用如下方法：

  • componentWillUnmount() 组件即将卸载和销毁前调用

错误处理

渲染过程，生命周期，或子组件的构造函数中抛出错误时，会调用如下方法：

  • static getDerivedStateFromError() 子组件抛出错误时调用

为什么不能在循环、条件或嵌套函数中调用 Hooks？ ​

核心结论：React Hooks 必须在组件的顶层作用域调用，不能出现在循环、条件判断或嵌套函数中。根本原因是 React 通过单向链表按调用顺序存储和查找所有 Hook 状态，一旦调用顺序发生变化，会导致状态错乱、程序崩溃等不可预测的错误。

一、底层原理：Hooks 基于链表按顺序存储

  1. 挂载阶段：按调用顺序构建链表 组件首次渲染时，每调用一个 Hook（如 useState、useEffect），React 都会创建一个对应的 Hook 对象，包含该 Hook 的状态、更新队列等信息，并将其按调用顺序追加到单向链表的尾部。

  2. 更新阶段：严格按相同顺序遍历链表 组件后续更新时，React 不会重新创建 Hook 对象，而是严格按照首次渲染时的调用顺序遍历链表，依次取出每个 Hook 的状态进行更新。

  3. 关键特性：React 是通过调用顺序而非变量名来识别不同 Hook 的。Hook 本身没有"命名"机制，React 不知道你给状态变量起了什么名字，只能通过它在链表中的位置来定位。

  • 首次渲染不会进行清理，会在下一次渲染，清除上一次的副作用。

  • 卸载阶段也会执行清除操作。

不管是哪个，我们都不希望这个返回值是异步的，这样我们无法预知代码的执行情况，很容易出现难以定位的 Bug。

所以 React 就直接限制了不能 useEffect 回调函数中不能支持 async...await...

由于 useEffect 是在函数式组件中承担执行副作用操作的职责，它的返回值的执行操作应该是可以预期的，而不能是一个异步函数，所以不支持回调函数 async...await 的写法。

我们可以将 async...await 的逻辑封装在 useEffect 回调函数的内部，这就是 ahooks useAsyncEffect 的实现思路，而且它的范围更加广，它支持的是所有的异步函数，包括 generator function。

简而言之：

  1. 缓存是有成本的，小的成本可能会累加过高。

  2. 默认缓存无法保证足够的正确性。

    1. 子组件已通过 React.memo 或 useMemo 被缓存

    2. 子组件所有的 prop 都被缓存

useMemo 和 useCallback 有什么区别？ ​

参考答案：

在 React 中，useMemo 和 useCallback 都是用来优化性能的钩子函数，但它们的用途和作用稍有不同。

1 useMemo: useMemo 的主要作用是在组件重新渲染时，用来缓存计算结果，以避免不必要的重复计算。它接收两个参数：一个回调函数和一个依赖数组。回调函数用于进行计算，而依赖数组用于指定在数组中列出的依赖项发生变化时，才重新计算并返回新的值，否则会返回上一次缓存的值。

2 useCallback: useCallback 的作用是在组件重新渲染时，返回一个记忆化的回调函数，以避免不必要的函数重新创建。它也接收两个参数：一个回调函数和一个依赖数组。当依赖项发生变化时，会返回一个新的回调函数，否则会复用之前的回调函数。

总结区别：

  • useMemo 主要用于缓存计算结果，适用于任何需要缓存值的场景。

  • useCallback 主要用于缓存回调函数，适用于需要传递给子组件的事件处理函数，以避免不必要的重新渲染。

另外，在大多数情况下，你不必在每个函数组件中都使用 useMemo 或 useCallback。

只有当你在性能测试中发现了性能问题，或者在特定情况下需要优化函数的创建和计算时，再考虑使用这些钩子。

useRef / ref / forwardsRef 的区别是什么? ​

参考答案：

useRef 和 ref 都是 React 中用于操作 DOM 元素或自定义组件实例的工具，而 forwardRef 则是用于访问嵌套子组件中的 DOM 元素或自定义组件实例。

它们之间的区别如下：

  1. useRef 是一个 hook 函数，可以在函数组件中使用；ref 是一个对象属性，只能在类组件中使用。

  2. useRef 返回一个可变的 ref 对象，可以在组件的整个生命周期内保持不变，也就是说不会因为重新渲染而改变。而 ref 每次渲染都会被重新创建。

  3. useRef 主要用于存储和更新组件内部状态，以及操作 DOM 元素。而 ref 主要用于获取 DOM 元素或自定义组件实例。

  4. forwardRef 是用于将 ref 属性“向下传递”给一个函数式子组件或自定义组件的工具函数。它允许父组件调用子组件中的 DOM 元素或自定义组件实例。

综上所述，useRef 和 ref 都是用于操作 DOM 元素或自定义组件实例的工具，与之相比，forwardRef 则是一个更高级的工具，用于处理专门的情况，即访问嵌套子组件中的 DOM 元素或自定义组件实例。

Redux中间件面试题核心总结 ​

核心定义：Redux中间件是对store.dispatch方法的增强，位于action发起后、reducer执行前的拦截点，解决了原生Redux只能处理同步action的问题，可扩展实现异步操作、日志记录、错误捕获、权限拦截等功能。

一、常用中间件

  1. redux-thunk：官方推荐的异步处理中间件，允许action creator返回一个函数而非普通对象，该函数接收dispatch和getState作为参数，可在内部执行网络请求等异步操作，完成后再派发同步action更新状态。
  2. redux-logger：开发调试中间件，自动记录每次派发的action信息以及更新前后的state状态，便于排查问题。

所有中间件通过applyMiddleware注册并组合成执行链，作为第二个参数传入createStore。

二、实现原理

  1. 中间件标准结构：每个中间件都是三层柯里化函数，签名为store => next => action => {}：

    • 第一层接收store的getState和dispatch方法
    • 第二层接收next（下一个中间件或原始dispatch）
    • 第三层接收action，执行具体逻辑后调用next(action)传递给下一个环节

  2. applyMiddleware核心逻辑：

    • 创建原始store实例
    • 将{ getState, dispatch }注入每个中间件
    • 使用compose函数将所有中间件组合成洋葱模型的执行链
    • 用组合后的函数替换原始dispatch，返回增强后的store

  3. redux-thunk极简原理：判断传入的action是否为函数，若是则执行该函数并传入dispatch和getState；若否则直接将action传递给下一个中间件。

Redux 理解与工作原理面试题核心总结 ​

核心定义：Redux是一个独立于UI框架的JavaScript状态管理库，用于集中管理应用的全局状态，解决了多组件间状态共享、状态变化追踪困难的问题。它遵循三大核心原则，通过单向数据流实现可预测的状态管理，常与React配合使用（通过react-redux库），也支持Vue等其他框架。

一、Redux三大核心原则

  1. 单一数据源：整个应用的所有状态都存储在唯一的store对象中，便于统一管理和调试
  2. State是只读的：不能直接修改state，只能通过派发action的方式触发状态更新，保证状态变化的可追踪性
  3. 使用纯函数Reducer执行修改：reducer是一个纯函数，接收旧state和action，返回新state，相同输入永远得到相同输出，无副作用

二、完整工作流程（单向数据流）

md
组件派发Action → Store接收Action并传递给Reducer → Reducer计算新State → Store更新State → 通知所有订阅组件 → 组件获取新State重新渲染
  • Action：描述"发生了什么"的普通JavaScript对象，必须包含type属性标识动作类型，可携带额外数据
  • Reducer：状态更新的"计算器"，根据action.type执行对应的状态更新逻辑，必须返回新的state对象（不能直接修改原state）
  • Store：连接Action和Reducer的核心容器，负责存储状态、派发Action、调用Reducer、通知订阅者

三、核心API

  1. createStore(reducer)：创建全局唯一的store实例
  2. store.dispatch(action)：派发Action，触发状态更新的唯一方式
  3. store.getState()：获取当前最新的state
  4. store.subscribe(callback)：订阅状态变化，当state更新时自动执行回调函数

说说React Router有几种模式，以及实现原理？ ​

React Router是React生态的官方路由库，专为单页应用设计，实现了不刷新页面即可改变URL并更新对应UI的核心能力，主要提供Hash模式和History模式两种路由实现。

Hash模式对应的组件是HashRouter，URL中会包含#符号，比如http://xxx.com/#/page1，它兼容所有浏览器包括低版本IE，不需要后端做任何配置。History模式对应的组件是BrowserRouter，URL中没有#符号，比如http://xxx.com/page1，它只兼容支持HTML5标准的浏览器，需要后端进行配置，否则刷新页面会出现404错误。两种模式的使用方式一致，都是作为应用的顶层组件包裹所有路由内容，通过路由规则组件定义路径与组件的映射关系。

Hash模式的核心是利用URL中#后面的hash值仅在客户端使用、不会被发送到服务器的特性，改变hash值不会触发页面刷新。它通过window.location.hash获取和修改当前hash值，监听全局的window.hashchange事件来捕获hash值的变化，当hash变化时更新内部的location状态，再通过Context将最新的路由信息传递给所有子组件，最后由路由匹配组件根据当前路径与配置的路径进行匹配，渲染对应的组件。

History模式基于HTML5新增的History API实现，允许开发者操作浏览器的会话历史记录。核心用到的API有history.pushState，用于添加一条新的历史记录且不刷新页面；history.replaceState，用于替换当前的历史记录且不刷新页面；还有window.popstate事件，用于监听浏览器前进、后退按钮的点击操作。它的实现流程是先拦截a标签的默认跳转行为，通过pushState或replaceState修改URL，同时监听popstate事件处理浏览器前进后退导致的URL变化，后续更新内部状态、传递路由信息和匹配渲染组件的流程与Hash模式一致。

需要注意的是，History模式需要后端配置的原因是，它的URL是真实的服务器路径，刷新页面时浏览器会向服务器请求该路径，因此后端需要将所有请求都重定向到应用的入口HTML文件。React Router使用path-to-regexp库将配置的路径字符串转换为正则表达式，实现路径的动态匹配和参数提取。React Router v6虽然废弃了Switch组件改用Routes组件，同时调整了Route组件的API，但两种路由模式的底层实现原理保持不变。

说说你对React Router的理解？常用的Router组件有哪些？ ​

React Router是React生态的官方前端路由库，专门用于构建单页应用，核心能力是实现URL变化时不刷新页面就能更新对应UI，让单页应用拥有和多页应用类似的页面切换和地址栏体验。它采用模块化的包结构，核心功能在react-router包中实现，基于核心包又衍生出适配不同运行环境的包，浏览器端使用react-router-dom，React Native端使用react-router-native，还有专门用于配置静态路由的工具库react-router-config。

react-router-dom提供了一系列常用的路由组件和API，首先是两个顶层路由容器组件BrowserRouter和HashRouter，它们作为整个应用的最外层组件包裹所有内容，负责监听浏览器URL的变化，并将最新的路由信息传递给所有子组件。其中BrowserRouter对应history模式，URL中没有#符号，体验更接近传统多页应用；HashRouter对应hash模式，URL中包含#符号，兼容性更好且不需要后端配置。

Route组件是定义路由规则的核心，用于建立URL路径和组件之间的映射关系，它提供了多个常用属性，path属性指定需要匹配的路径，component属性指定匹配成功后要渲染的组件，render属性可以直接写渲染逻辑，exact属性用于开启精准匹配，只有当路径完全一致时才会渲染对应的组件，避免路径前缀匹配导致的错误。

导航相关的组件主要有Link和NavLink，Link组件最终会被渲染成a标签，用to属性代替原生a标签的href属性，实现无刷新的页面跳转。NavLink是Link的增强版本，专门用于导航菜单，支持设置activeStyle和activeClassName属性，当对应的路由匹配成功时，会自动为渲染出的a标签添加指定的样式或类名，实现导航项的高亮效果。如果需要通过JavaScript代码实现页面跳转，可以使用history对象提供的push、replace、goBack、goForward等方法，在函数组件中可以通过useHistory钩子直接获取history对象，不需要通过组件props传递。

Redirect组件用于实现路由重定向，当这个组件被渲染时，会自动跳转到to属性指定的路径，常用于权限控制，比如未登录用户访问受保护页面时重定向到登录页，也可以用于设置应用的默认跳转路径。Switch组件用于包裹多个Route组件，它的作用是保证只渲染第一个匹配成功的Route组件，避免多个路由同时匹配导致多个组件一起渲染的问题，通常会在Switch的最后放置一个没有path属性的Route组件，作为404页面的兜底路由。

除了组件之外，react-router-dom还提供了多个实用的钩子函数，useParams用于获取动态路由中的参数，useLocation用于获取当前的location对象，包含当前路径、查询参数、状态等完整的URL信息。

路由参数传递主要有三种方式，第一种是动态路由，在Route的path属性中用:参数名的形式定义动态部分，比如/detail/:id，跳转时在路径中传入具体的参数值，在目标组件中通过useParams获取对应的参数。第二种是search参数，在跳转路径后面拼接?key=value形式的查询字符串，在目标组件中通过location.search获取后再解析成对象使用。第三种是通过to属性传入对象的方式传递参数，对象中可以包含pathname、search、query、state等属性，其中state属性传递的参数不会出现在URL中，适合传递敏感或不需要暴露的信息，所有参数都可以通过location对象获取。

  1. 解题思路
    1. 文档处理阶段
      • 文档加载阶段：需要支持多种文档格式的解析，包括PDF、Markdown、文本文件等。可以使用langchain提供的各种loader，如PyPDFLoader用于PDF解析、MarkdownLoader用于Markdown文件解析等。对于特殊格式的文档，可能需要自定义Loader来实现解析逻辑
      • 文档切分阶段：这是影响检索效果的关键步骤。需要将长文档切分成合适大小的块（Chunks），通常建议块大小为1000-2000个字符，并设置10%-20%的重叠量（chunkOverlap）以保持语义的连续性。切分策略可以采用递归切分方法，优先在段落分隔符、标题等位置进行切分，避免在句子中间断开。
      • 向量化：是将文本转换为向量表示的过程，这使得计算机能够理解文本的语义。可以使用OpenAIEmbeddings、HuggingFaceEmbeddings等模型来生成文本的向量表示。向量的维度通常为1536维（OpenAI的text-embedding-ada-002模型），这个维度能够很好地捕捉文本的语义信息。
      • 向量存储：需要选择合适的向量数据库。在前端场景下，可以使用Chroma、Pinecone等轻量级的向量数据库。Chroma适合本地部署和小规模应用，而Pinecone则适合大规模和分布式场景。向量数据库需要支持高效的相似性搜索，通常使用余弦相似度或点积来计算向量之间的相似度
    2. 文档检索阶段
      • 检索阶段：需要实现高效的相似度搜索算法。可以使用近似最近邻搜索（ANN）算法来提高搜索速度，如HNSW（分层可导航小世界）算法。同时要实现多路召回策略，结合关键词搜索和语义搜索，提高检索的准确性
      • 生成阶段：需要将检索到的相关文档作为上下文，与用户问题一起发送给LLM生成最终回答。这个过程中要注意上下文窗口的限制，确保总Token数不超过模型的限制。可以使用文档摘要或关键信息提取的方法来减少上下文的大小

聊聊 vite 和 webpack 的区别 ​

参考答案：

Vite 和 Webpack 都是前端打包工具，它们的作用类似，但实现方式和使用方法有所不同。以下是它们之间的一些区别：

  1. 构建速度：Vite 的构建速度比 Webpack 更快，因为 Vite 在开发环境下使用了浏览器原生的 ES 模块加载，而不是像 Webpack 一样使用打包后的文件进行模块加载。在 Vite 中，每个模块都可以独立地进行编译和缓存，这意味着它只需要重新编译修改过的模块，而不是整个应用程序。这使得 Vite 开发起来更加高效。

  2. 配置复杂度：Vite 的配置相对更简单，因为它无需进行大量的配置，只需指定一些基本的选项就可以开始开发。Webpack 的配置更加复杂，需要针对具体项目进行不同的配置，且需要理解各种插件、Loader 等概念。

  3. 生态环境：Webpack 的生态环境更加成熟，在社区中拥有广泛的支持和丰富的插件库。而 Vite 尚处于发展阶段，尽管其已经获得了很多关注，但其生态系统仍然不太完善。

  4. 功能特性：Webpack 是一个功能更加全面的打包工具，支持各种 Loader 和插件，可以处理多种类型的文件和资源。而 Vite 的设计初衷是专注于开发环境下的快速构建，因此其对一些高级特性的支持相对较少。

综上所述，Vite 更适合用于开发环境下的快速构建，而 Webpack 则更适合用于生产环境下的复杂应用程序的打包处理。选择使用哪种工具需要根据具体项目需求进行评估。

webpack的构建流程是什么 ​

参考答案：

Webpack 的运行流程是一个串行的过程，从启动到结束会依次执行以下流程：

  1. 初始化参数：从配置文件和 Shell 语句中读取与合并参数，得出最终的参数；

  2. 开始编译：用上一步得到的参数初始化 Compiler 对象，加载所有配置的插件，执行对象的 run 方法开始执行编译；

  3. 确定入口：根据配置中的 entry 找出所有的入口文件；

  4. 编译模块：从入口文件出发，调用所有配置的 Loader 对模块进行翻译，再找出该模块依赖的模块，再递归本步骤直到所有入口依赖的文件都经过了本步骤的处理；

  5. 完成模块编译：在经过第4步使用 Loader 翻译完所有模块后，得到了每个模块被翻译后的最终内容以及它们之间的依赖关系；

  6. 输出资源：根据入口和模块之间的依赖关系，组装成一个个包含多个模块的 Chunk，再把每个 Chunk 转换成一个单独的文件加入到输出列表，这步是可以修改输出内容的最后机会；

  7. 输出完成：在确定好输出内容后，根据配置确定输出的路径和文件名，把文件内容写入到文件系统。

webpack的Loader和Plugin的不同 ​

参考答案：

不同的作用:

  • Loader直译为"加载器"。Webpack将一切文件视为模块，但是webpack原生是只能解析js文件，如果想将其他文件也打包的话，就会用到loader。 所以Loader的作用是让webpack拥有了加载和解析非JavaScript文件的能力。

  • Plugin直译为"插件"。Plugin可以扩展webpack的功能，让webpack具有更多的灵活性。 在 Webpack 运行的生命周期中会广播出许多事件，Plugin 可以监听这些事件，在合适的时机通过 Webpack 提供的 API 改变输出结果。

不同的用法:

  • Loader在module.rules中配置，也就是说他作为模块的解析规则而存在。 类型为数组，每一项都是一个Object，里面描述了对于什么类型的文件（test），使用什么加载(loader)和使用的参数（options）

  • Plugin在plugins中单独配置。 类型为数组，每一项是一个plugin的实例，参数都通过构造函数传入。

Webpack中 loader的作用是什么，以及常用loader有哪些 ​

参考答案：

（2）可以编译文件，从而使其能够添加到依赖关系中。loader是 WebPack最重要的部分之一。通过使用不同的 loader，我们能够调用外部的脚本或者工具，实现对不同格式文件的处理。loader需要在 webpack.config.js里单独用 module进行配置。

treeShaking ​

Tree shaking是webpack的死代码消除技术，用于清除项目中未被使用的冗余代码，大幅减小最终打包体积。

它的实现完全依赖ES6的静态模块系统：ES6的import/export是编译时静态加载的语法，只能在代码顶层使用，不能出现在条件判断等动态逻辑中，这使得webpack可以在代码运行前，静态分析出完整的依赖关系树。

核心原理分为两步：首先webpack在编译阶段对所有ES6模块进行静态解析，构建整个项目的依赖图；然后通过静态分析程序流，标记出所有从未被引用和调用的模块、函数、变量，最后在打包压缩阶段将这些未使用的死代码从最终产物中删除。

而CommonJS的require是运行时动态加载的，无法在编译阶段确定完整的依赖关系，因此不支持tree shaking。

什么是 CI/CD？ ​

参考答案：

CI/CD是持续集成（Continuous Integration）和持续交付/持续部署（Continuous Delivery/Continuous Deployment）的缩写。

  • 持续集成（Continuous Integration，CI）：CI是一种开发实践，通过频繁地将代码集成到共享的版本控制库中，并自动进行构建、测试和静态代码分析等过程，以早期发现和解决代码集成问题。主要目标是减少集成冲突和快速反馈，提高开发团队的协作效率和代码质量。

  • 持续交付/持续部署（Continuous Delivery/Continuous Deployment，CD）：CD是在CI的基础上进一步自动化整个软件交付流程的实践。持续交付指将软件交付到可部署环境的过程，包括自动化构建、自动化测试、文档生成和打包等，以确保每次交付都是可靠和可重复的。持续部署则更进一步，指将软件自动部署到生产环境，从而减少人工干预和降低发布的风险。

CI/CD的目标是通过自动化和持续的流程来提高软件开发和交付的效率、质量和可靠性。它帮助团队集中精力于开发新功能，并能够快速、频繁地将这些功能交付给最终用户。CI/CD在现代软件开发中被广泛采用，为团队提供了一种更加可靠和高效的软件交付方式。

Vite 高频面试题核心总结 ​

Vite 是新一代前端构建工具，基于原生 ES 模块和esbuild/Rollup 实现，核心解决了 Webpack 开发环境启动慢、热更新慢的痛点，现已成为 Vue3、React 项目的首选构建工具。

一、Vite 与 Webpack 的核心区别 ​

  1. 构建原理不同：Webpack 是先打包再启动开发服务器，启动时需要遍历所有依赖并完成打包，项目越大启动越慢；Vite 是先启动开发服务器，再按需编译，利用浏览器原生支持的 ES 模块，只在浏览器请求某个文件时才进行编译，启动速度几乎不受项目大小影响。
  2. 热更新机制不同：Webpack 热更新需要重新构建整个模块依赖链，项目越大热更新越慢；Vite 热更新只需要重新编译发生变化的单个文件，热更新速度恒定，与项目规模无关。
  3. 生产环境打包不同：Webpack 生产环境使用自身的打包器；Vite 生产环境使用 Rollup 进行打包，Rollup 对 ES 模块的优化更好，打包产物更小、更干净。
  4. 依赖处理不同：Vite 会对第三方依赖进行预构建，将 CommonJS/UMD 格式的依赖转换为 ES 模块，同时将多个内部模块的依赖打包成单个文件，减少浏览器的请求数量；Webpack 会将所有依赖和业务代码一起打包。

二、Vite 的工作原理 ​

Vite 将开发环境和生产环境做了分离，采用不同的构建策略：

  1. 开发环境：
    • 启动一个基于 Koa 的轻量级开发服务器
    • 对第三方依赖进行预构建（使用 esbuild），转换为 ES 模块并缓存
    • 拦截浏览器的 ES 模块请求，对业务代码进行实时编译（如 Vue 单文件组件、TS、JSX 等）
    • 编译后的代码直接返回给浏览器，由浏览器负责模块加载和执行
  2. 生产环境：
    • 使用 Rollup 进行完整的打包构建
    • 自动进行代码分割、tree shaking、压缩等优化
    • 生成兼容现代浏览器的静态资源

三、依赖预构建的作用与实现 ​

Vite 在首次启动时会自动进行依赖预构建，这是 Vite 性能优异的核心原因之一：

  1. 核心作用：
    • 转换模块格式：将 CommonJS/UMD 格式的第三方依赖转换为浏览器可识别的 ES 模块
    • 减少请求数量：将包含多个内部模块的依赖（如 lodash）打包成单个文件，避免浏览器发起大量并行请求导致的性能问题
    • 缓存优化：预构建后的依赖会被缓存到本地，只有当依赖版本发生变化时才会重新构建
  2. 实现方式：使用 esbuild 进行预构建，esbuild 是用 Go 语言编写的构建工具，速度比 JavaScript 编写的构建工具快 10-100 倍。

四、Vite HMR（热更新）的原理 ​

Vite 的 HMR 基于 ES 模块实现，比 Webpack 的 HMR 更高效：

  1. 当文件发生变化时，Vite 会精确找到发生变化的模块及其相关的依赖
  2. 只重新编译发生变化的单个模块，然后通过 WebSocket 通知浏览器
  3. 浏览器接收到通知后，重新请求更新后的模块，替换旧模块并重新渲染
  4. 整个过程不需要重新加载页面，也不需要重新构建其他未变化的模块，因此速度极快

五、为什么生产环境用 Rollup 而不是 esbuild ​

虽然 esbuild 速度极快，但 Vite 生产环境仍然选择 Rollup，主要原因是：

  1. esbuild 的生态不如 Rollup 成熟，缺少很多生产环境需要的优化功能
  2. Rollup 对 ES 模块的优化更彻底，tree shaking 效果更好，打包产物更小
  3. Rollup 拥有更丰富的插件生态，可以满足各种复杂的构建需求
  4. esbuild 对代码分割、CSS 处理等功能的支持还不够完善

六、Vite 的插件系统 ​

Vite 的插件系统基于 Rollup 的插件系统设计，同时扩展了一些 Vite 特有的钩子：

  1. 完全兼容大部分 Rollup 插件，可以直接使用
  2. 提供了开发环境特有的钩子，如 configureServer（配置开发服务器）、transformIndexHtml（转换 HTML 文件）等
  3. 插件可以同时作用于开发环境和生产环境，无需编写两套逻辑

七、Vite 常见优化手段 ​

  1. 优化依赖预构建：通过 optimizeDeps 配置手动指定需要预构建的依赖，排除不需要预构建的依赖
  2. 代码分割：使用动态导入 import() 进行路由懒加载，将大组件拆分成更小的 chunk
  3. 静态资源优化：通过 build.assetsInlineLimit 配置将小图片内联为 base64，减少请求数量
  4. 生产环境压缩：开启 build.minify 进行代码压缩，使用 terser 或 esbuild 作为压缩工具
  5. 使用 CDN：将大型第三方库通过 CDN 引入，减少打包体积

八、其他高频考点 ​

  1. 环境变量处理：Vite 使用 import.meta.env 访问环境变量，支持 .env、.env.development、.env.production 等多环境配置文件，只有以 VITE_ 开头的变量才会被暴露给客户端。
  2. 静态资源处理：Vite 支持直接导入图片、字体、JSON 等静态资源，导入后会返回资源的 URL，同时支持 ?raw、?url、?worker 等查询参数实现特殊导入。
  3. 兼容低版本浏览器：使用 @vitejs/plugin-legacy 插件，自动生成兼容传统浏览器的代码，并根据浏览器支持情况自动加载对应的版本。

设计模式 ​

1. 观察者模式和发布订阅模式分别是什么？有什么区别？ ​

观察者模式：一个对象（观察者）订阅另一个对象（主题），当主题被激活的时候，触发观察者里面的事件。

发布订阅模式：订阅者把自己想要订阅的事件注册到调度中心，当发布者发布事件到调度中心（就是该事件被触发），再由调度中心统一调度订阅者注册到调度中心的处理代码。

可以发现两种模式下的角色数量不一样：

  • 观察者模式里，只有两个角色：观察者 和 被观察者

  • 发布订阅模式里，却不仅仅只有发布者和订阅者两个角色，还有一个调度中心

从使用场景上：

  • 观察者模式比较适合在单个应用内部使用

  • 发布订阅模式则是比较适合跨应用的场景

2. 开发的过程中你用到过哪些设计模式？ ​

参考答案：

设计模式是一种被广泛接受并经过验证的面向对象软件开发中的最佳实践。它们提供了一套解决常见问题的可重用设计方案。

以下是一些常用的设计模式：

  1. 单例模式（Singleton）：确保一个类只有一个实例，并提供全局访问点来获取该实例。

  2. 工厂模式（Factory）：通过工厂方法创建对象，而不是直接使用new操作符。这样可以隐藏具体实现，并根据需要创建所需类型的对象。

  3. 观察者模式（Observer）：定义了一种一对多的依赖关系，当一个对象状态发生改变时，它的所有依赖者（观察者）都会收到通知并自动更新。

  4. 装饰器模式（Decorator）：动态地将责任附加到对象上。通过将对象包装在装饰器对象中，可以在运行时为对象添加新的行为。

  5. 策略模式（Strategy）：定义了一系列算法，将每个算法封装起来并使它们可以相互替换。策略模式可以让算法独立于客户端而变化。

  6. 适配器模式（Adapter）：将一个类的接口转换成客户端所期望的另一个接口。适配器模式使得原本由于接口不匹配而无法一起工作的类可以协同工作。

每个设计模式都有其特定的应用场景和优缺点，可以根据具体情况来选择使用。设计模式可以提高代码结构的灵活性、可维护性和可扩展性，并促进重用和解耦。然而，需要根据实际需求慎重选择和应用设计模式，避免过度设计或不必要的复杂性。

4. 什么是 MVVM？比之 MVC 有什么区别？什么又是 MVP ？ ​

参考答案：

MVC、MVP 和 MVVM 是三种常见的软件架构设计模式，主要通过分离关注点的方式来组织代码结构，优化我们的开发效率。

比如说我们实验室在以前项目开发的时候，使用单页应用时，往往一个路由页面对应了一个脚本文件，所有的页面逻辑都在一个脚本文件里。页面的渲染、数据的获取，对用户事件的响应所有的应用逻辑都混合在一起，这样在开发简单项目时，可能看不出什么问题，当时一旦项目变得复杂，那么整个文件就会变得冗长，混乱，这样对我们的项目开发和后期的项目维护是非常不利的。

MVC 通过分离 Model、View 和 Controller 的方式来组织代码结构。其中 View 负责页面的显示逻辑，Model 负责存储页面的业务数据，以及对相应数据的操作。并且 View 和 Model 应用了观察者模式，当 Model 层发生改变的时候它会通知有关 View 层更新页面。Controller 层是 View 层和 Model 层的纽带，它主要负责用户与应用的响应操作，当用户与页面产生交互的时候，Co ntroller 中的事件触发器就开始工作了，通过调用 Model 层，来完成对 Model 的修改，然后 Model 层再去通知 View 层更新。

MVP 模式与 MVC 唯一不同的在于 Presenter 和 Controller。在 MVC 模式中我们使用观察者模式，来实现当 Model 层数据发生变化的时候，通知 View 层的更新。这样 View 层和 Model 层耦合在一起，当项目逻辑变得复杂的时候，可能会造成代码的混乱，并且可能会对代码的复用性造成一些问题。MVP 的模式通过使用 Presenter 来实现对 View 层和 Model 层的解耦。MVC 中的 Controller 只知道 Model 的接口，因此它没有办法控制 View 层的更新，MVP 模式中，View 层的接口暴露给了 Presenter 因此我们可以在 Presenter 中将 Model 的变化和 View 的变化绑定在一起，以此来实现 View 和 Model 的同步更新。这样就实现了对 View 和 Model 的解耦，Presenter 还包含了其他的响应逻辑。

MVVM 模式中的 VM，指的是 ViewModel，它和 MVP 的思想其实是相同的，不过它通过双向的数据绑定，将 View 和 Model 的同步更新给自动化了。当 Model 发生变化的时候，ViewModel 就会自动更新；ViewModel 变化了，View 也会更新。这样就将 Presenter 中的工作给自动化了。我了解过一点双向数据绑定的原理，比如 vue 是通过使用数据劫持和发布订阅者模式来实现的这一功 能。

5. 单例模式 ​

参考答案：

1.什么是单例

  • 保证一个类只有一个实例，并且提供一个访问该全局访问点

    2.那些地方用到了单例模式

  1. 网站的计数器，一般也是采用单例模式实现，否则难以同步。

  2. 应用程序的日志应用，一般都是单例模式实现，只有一个实例去操作才好，否则内容不好追加显示。

  3. 多线程的线程池的设计一般也是采用单例模式，因为线程池要方便对池中的线程进行控制

  4. Windows的（任务管理器）就是很典型的单例模式，他不能打开俩个

  5. windows的（回收站）也是典型的单例应用。在整个系统运行过程中，回收站只维护一个实例。

3.单例优缺点

优点：

  1. 在单例模式中，活动的单例只有一个实例，对单例类的所有实例化得到的都是相同的一个实例。这样就防止其它对象对自己的实例化，确保所有的对象都访问一个实例

  2. 单例模式具有一定的伸缩性，类自己来控制实例化进程，类就在改变实例化进程上有相应的伸缩性。

  3. 提供了对唯一实例的受控访问。

  4. 由于在系统内存中只存在一个对象，因此可以节约系统资源，当需要频繁创建和销毁的对象时单例模式无疑可以提高系统的性能。

  5. 允许可变数目的实例。

  6. 避免对共享资源的多重占用。

缺点：

  1. 不适用于变化的对象，如果同一类型的对象总是要在不同的用例场景发生变化，单例就会引起数据的错误，不能保存彼此的状态。

  2. 由于单利模式中没有抽象层，因此单例类的扩展有很大的困难。

  3. 单例类的职责过重，在一定程度上违背了“单一职责原则”。

  4. 滥用单例将带来一些负面问题，如为了节省资源将数据库连接池对象设计为的单例类，可能会导致共享连接池对象的程序过多而出现连接池溢出；如果实例化的对象长时间不被利用，系统会认为是垃圾而被回收，这将导致对象状态的丢失。

5.单例创建方式

（主要使用懒汉和懒汉式）

  1. 饿汉式:类初始化时,会立即加载该对象，线程天生安全,调用效率高。

  2. 懒汉式: 类初始化时,不会初始化该对象,真正需要使用的时候才会创建该对象,具备懒加载功能。

6. 设计模式的六大原则 ​

参考答案：

开放封闭原则（Open Close Principle）

  • 原则思想：尽量通过扩展软件实体来解决需求变化，而不是通过修改已有的代码来完成变化

  • 描述：一个软件产品在生命周期内，都会发生变化，既然变化是一个既定的事实，我们就应该在设计的时候尽量适应这些变化，以提高项目的稳定性和灵活性。

  • 优点：单一原则告诉我们，每个类都有自己负责的职责，里氏替换原则不能破坏继承关系的体系。

里氏代换原则（Liskov Substitution Principle）

  • 原则思想：使用的基类可以在任何地方使用继承的子类，完美的替换基类。

  • 大概意思是：子类可以扩展父类的功能，但不能改变父类原有的功能。子类可以实现父类的抽象方法，但不能覆盖父类的非抽象方法，子类中可以增加自己特有的方法。

  • 优点：增加程序的健壮性，即使增加了子类，原有的子类还可以继续运行，互不影响。

依赖倒转原则（Dependence Inversion Principle）

  • 依赖倒置原则的核心思想是面向接口编程.

  • 依赖倒转原则要求我们在程序代码中传递参数时或在关联关系中，尽量引用层次高的抽象层类，

  • 这个是开放封闭原则的基础，具体内容是：对接口编程，依赖于抽象而不依赖于具体。

接口隔离原则（Interface Segregation Principle）

  • 这个原则的意思是：使用多个隔离的接口，比使用单个接口要好。还是一个降低类之间的耦合度的意思，从这儿我们看出，其实设计模式就是一个软件的设计思想，从大型软件架构出发，为了升级和维护方便。所以上文中多次出现：降低依赖，降低耦合。

  • 例如：支付类的接口和订单类的接口，需要把这俩个类别的接口变成俩个隔离的接口

迪米特法则（最少知道原则）（Demeter Principle）

  • 原则思想：一个对象应当对其他对象有尽可能少地了解，简称类间解耦

  • 大概意思就是一个类尽量减少自己对其他对象的依赖，原则是低耦合，高内聚，只有使各个模块之间的耦合尽量的低，才能提高代码的复用率。

  • 优点：低耦合，高内聚。

单一职责原则（Principle of single responsibility）

  • 原则思想：一个方法只负责一件事情。

  • 描述：单一职责原则很简单，一个方法 一个类只负责一个职责，各个职责的程序改动，不影响其它程序。 这是常识，几乎所有程序员都会遵循这个原则。

  • 优点：降低类和类的耦合，提高可读性，增加可维护性和可拓展性，降低可变性的风险。

7. 工厂模式 ​

参考答案：

1.什么是工厂模式

  • 它提供了一种创建对象的最佳方式。在工厂模式中，我们在创建对象时不会对客户端暴露创建逻辑，并且是通过使用一个共同的接口来指向新创建的对象。实现了创建者和调用者分离，工厂模式分为简单工厂、工厂方法、抽象工厂模式

    2.工厂模式好处

  • 工厂模式是我们最常用的实例化对象模式了，是用工厂方法代替new操作的一种模式。

  • 利用工厂模式可以降低程序的耦合性，为后期的维护修改提供了很大的便利。

  • 将选择实现类、创建对象统一管理和控制。从而将调用者跟我们的实现类解耦。
